## Доменная модель и доступ

Бот поддерживает два типа обращений:

1. **Открытое:** сохраняются ключ сотрудника, ФИО и должность на момент отправки.
2. **Анонимное:** в строке обращения сохраняются только текст, время и техническое состояние доставки; поля автора принудительно обнуляются.

Доступ разрешён только в личном чате и только Telegram ID из allowlist. Новое обращение доставляется одному заданному получателю. История всех обращений доступна трём администраторам.

Анонимность реализована корректно **на уровне прикладной базы**:

- в таблице вообще нет колонки Telegram ID автора;
- код передаёт `None` для всех полей автора анонимного обращения;
- SQL `CHECK` запрещает сохранить анонимную запись с заполненными полями автора;
- отдельный тест подтверждает отсутствие данных автора.

Это не криптографическая и не платформенная анонимность: Telegram видит взаимодействие пользователя с ботом, а во время заполнения состояние диалога связано с Telegram ID в оперативной памяти процесса. В новой платформе это ограничение должно быть честно отражено в политике конфиденциальности.

## Доставка и надёжность

Положительные свойства:

- HTML пользовательского текста и ФИО экранируется;
- локальный `asyncio.Lock` защищает от двух одновременных отправок одной записью в одном процессе;
- успешно доставленная запись повторно не отправляется;
- ошибка Telegram сохраняется и не удаляет обращение.

Открытые риски:

1. Повторы бесконечны: нет лимита попыток, exponential backoff и dead-letter состояния.
2. При падении процесса после успешного `send_message`, но до `mark_delivered`, сообщение может быть доставлено повторно после запуска.
3. Worker берёт только первые 20 pending-записей; большое число постоянно ошибочных старых записей способно задержать последующие.
4. Блокировка действует только внутри одного процесса; две одновременно запущенные копии не координируются.
5. FSM хранится только в памяти: перезапуск сбрасывает незавершённое обращение.

Для новой платформы нужны идемпотентный outbox, ограниченные повторы, backoff, dead-letter очередь, административное восстановление и наблюдаемость доставки.

## Characterisation-сценарии для новой платформы

1. Пользователь вне allowlist и групповой чат не получают доступ.
2. Анонимное обращение не сохраняет идентификатор, имя, должность или косвенную привязку автора в прикладном хранилище и аудите.
3. Открытое обращение сохраняет снимок данных автора на момент отправки.
4. Пустой, нетекстовый или превышающий лимит ввод отклоняется.
5. Пользователь может проверить, изменить, отменить и подтвердить обращение.
6. Новая запись доставляется только утверждённому получателю.
7. История доступна только утверждённым администраторам и сортируется от новых к старым.
8. Пользовательский текст безопасно отображается и не интерпретируется как HTML.
9. Временная ошибка доставки не теряет обращение и повторяется по управляемой политике.
10. Перезапуск в любой точке доставки не создаёт неконтролируемых дублей.
11. Повторный импорт в PostgreSQL идемпотентен и сохраняет признаки анонимности, времена и состояние доставки.
12. Анонимность и её ограничения одинаково ясно объяснены на всех трёх языках интерфейса.

## Обязательные действия

### Критично

1. Не публиковать и не передавать текущий portable ZIP: внутри находится рабочий Telegram-токен.
2. Не вращать токен без согласования с действующим ботом; перед следующим развёртыванием выпустить новый токен и одновременно обновить production-конфигурацию.
3. Удалить копирование `.env` из будущего build/package-процесса; секрет задавать только на целевой машине.
4. Не включать реальный `employees.json` в Git или публичные артефакты.

### До миграции

1. Найти рабочую папку/базу с реальными обращениями и скопировать её при остановленном боте либо штатным SQLite backup.
2. Зафиксировать хеши базы, журнала, конфигурации и фактической production-сборки.
3. Получить подтверждение владельца полноты снимка и ожидаемой модели анонимности.
4. Определить срок хранения обращений, круг администраторов, правила экспорта и удаления.
