# Проверки Pull Request

CI запускается для каждого PR в main. Новый push отменяет предыдущий запуск
того же PR; параллельные PR друг друга не отменяют.

Перед дорогими заданиями проверяются заметки обновления и правила выбора проверок.
Обязательные статусы сохраняются: python, desktop, secrets. Ошибка или отмена
preflight, релевантного задания или тестового шарда не может дать зелёный статус.

## Какие задания запускаются

| Изменения | Python | Desktop |
| --- | --- | --- |
| apps/api, modules, tests/python, Python-зависимости | Да | Нет |
| apps/desktop, кроме собственной pending-заметки | Нет | Да |
| docs, README.md, AGENTS.md, CONTRIBUTING.md, LICENSE, pending-заметки | Нет | Нет |
| Общие packages, workflow, scripts, инфраструктура, корневые настройки и неизвестные пути | Да | Да |
| Ручной workflow_dispatch или пустой diff | Да | Да |

Смешанные изменения объединяют нужные области. Сравнивается полный diff PR
от merge base, а не только последний коммит. Для переименования учитываются
старый и новый пути. Ошибка чтения diff блокирует CI.

Secrets проверяется на каждом PR независимо от выбранных областей.
Пропуск нерелевантного набора подтверждается обязательным итоговым заданием;
workflow целиком не пропускается, чтобы required checks не оставались Pending.

## Desktop-тесты

Все тестовые файлы сохраняются в запуске. Четыре Windows-шарда выполняют их
по одному процессу на раннер: увеличение параллелизма внутри раннера ранее
вызывало нехватку памяти и нестабильные UI-таймеры.

Лимит workers задаётся через CLI, а не через наследуемый конфиг проектов:
обычный pnpm test сохраняет локальный лимит 4, CI явно передаёт --maxWorkers=1.
Иначе проект унаследует локальное значение и переопределит ограничение CI.

Явный список в apps/desktop/vitest.node-tests.mts содержит проверки без DOM:
вычисления и контракты исходников/CSS. Они используют Node без jsdom и
Fluent/Tabster setup. Все остальные, в том числе новые тесты, по умолчанию
используют прежнюю UI-среду. Изоляция тестовых файлов остаётся включённой.

`BalancedSequencer` распределяет полный обнаруженный Vitest набор по четырём
шардам методом longest-processing-time first. Оценки в
`apps/desktop/ci-test-timings.json` взяты из успешного Windows CI: учитывается
интервал между завершениями файлов, включая imports/setup/jsdom, а не только
время assertions. Самые тяжёлые файлы расходятся по разным раннерам.
Ключ — имя проекта и относительный путь, одинаковый на Windows и Linux.
Новые/переименованные файлы получают запасную оценку и всегда включаются;
удалённые записи в оценках не запускают несуществующие файлы. Без `--shard`
порядок и набор локального запуска остаются стандартными Vitest.

Оценки фиксированы в Git: все четыре раннера должны читать одинаковые данные.
Для обновления после успешного полного запуска (нужен авторизованный `gh`):

```powershell
node scripts/ci/update-test-timings.mjs RUN_ID
```

Скрипт требует четыре успешных шарда и отклоняет пустые/дублирующиеся результаты.
Изменённый manifest нужно просмотреть и закоммитить обычным PR. Не обновлять
его независимо в каждом шарде: разные оценки могут привести к пропускам/дублям.
Балансировка не меняет worker limits, таймауты, isolation или состав проверок.

Интеграционные сценарии оболочки разделены на семь `App.*.test.tsx` по областям:
shell/auth, messaging, notifications, task planning, task review, approvals и
modules. Общий `app-test-harness.tsx` сохраняет серверные fixtures, renderer и
одинаковый afterEach (cleanup, Tabster, Griffel, storage,
globals/mocks). Все 57 исходных объявлений (58 случаев с `it.each`) перенесены
без сокращения проверок. Тест удаления задачи ожидает появление карточки и
действия удаления при первом холодном открытии раздела, а не зависит от
предыдущего сценария, прогревшего React.lazy. Первые сценарии создания/удаления
задачи завершают настоящий асинхронный переход React.lazy через async act;
таймауты не увеличиваются. Изоляция файлов не отключается.
Каждая группа импортирует настоящий App и предзагружает только собственные
workflow-модули при сборе тестов: чужие тяжёлые разделы не загружаются в каждом
изолированном файле. Никакие UI-компоненты не подменяются заглушками.
Оценки новых групп калибруются по длительности файлов в диагностическом Windows
запуске; их происхождение отмечено в `splitSuiteEstimates` manifest.
Обычное обновление замеров заменяет их результатами полного Windows CI.

Локальные команды из корня:

```powershell
pnpm test:workflow
pnpm test:app
pnpm --filter @yuksalish/desktop exec vitest run --project node --maxWorkers=1
pnpm --filter @yuksalish/desktop exec vitest run --shard=1/4 --maxWorkers=1
```

Сравнивать ускорение нужно по длительности заданий и фазам Vitest из логов,
учитывая повторные попытки и очередь GitHub. До оптимизации CI #621 для PR #225
занял 12:03; самый долгий renderer-шард — 11:51, из них шаг тестов — 10:32.
