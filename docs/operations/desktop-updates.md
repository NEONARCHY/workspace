# Обновления Windows-приложения

Обновление хранится на собственном сервере Yuksalish, не собирается на ПК сотрудников и не подтягивается автоматически из GitHub. Разработчик собирает новую версию, проверяет её, затем суперадминистратор загружает установщик в «Профиль → Обновления приложения» и публикует. Только после публикации клиенты начинают скачивание. Отдельная кнопка включает или выключает блокировку устаревших версий.

## Перед первым запуском

1. Развернуть один сервер API и PostgreSQL. Применить Alembic-миграции, включая `0025_desktop_updates`. Миграция ограничивает число суперадминистраторов одним. Если такой пользователь уже есть, команда ниже не заменит и не повысит его автоматически — сначала проверьте учётные записи вручную.
2. Обеспечить постоянную директорию установщиков и резервировать её вместе с базой данных. В штатном Docker Compose используется том `desktop-updates` в `/workspace/var/desktop-updates`, а gateway разрешает потоковую загрузку до 350 МиБ. При запуске API вне Compose указать абсолютный путь через `YUKSALISH_UPDATE_DIRECTORY`, доступный для записи процессу API. Относительный путь `var/desktop-updates` подходит только для разработки.
3. Для ПК коллег предоставить API по постоянному адресу HTTPS с доверенным на каждом клиенте сертификатом. При сборке клиента установить `VITE_API_BASE_URL` в этот адрес, **без `/api/v1` и завершающего `/`**. Для переноса LAN-сервера см. [универсальную инструкцию](lan-server-transfer.md): адрес вида `https://192.168.1.50:8443` и внутренний корневой сертификат. Установщик, собранный с локальным `127.0.0.1`, не сможет получать обновления с другого компьютера. Обновления по незащищённому HTTP вне локального ПК клиент отвергает.
4. На серверном ПК, после миграции и до выдачи доступов, один раз запустить `yuksalish-provision-admins --superadmin-username baxtiyorsamugov --superadmin-name "Бахтиёр Самугов" --admin-username almazovtemur --admin-name "Темур Алмазов"` внутри окружения API. Команда запросит пароли дважды со скрытым вводом; не передавайте их аргументами, переменными окружения или через Git. Если учётные записи уже существуют, скрипт откажется менять роли/пароли. Включите TOTP при первом входе.

## Выпуск версии

1. При каждом push и в каждом Pull Request Codex добавляет собственный файл в `apps/desktop/release-notes/pending/` с датой в начале имени (`YYYYMMDD-...json`), уникальным `id` и 1–12 короткими пунктами на понятном пользователю языке. Разные PR не редактируют один общий список, поэтому при параллельном merge их тексты не затирают друг друга. CI блокирует push/PR без нового или обновлённого pending-блока.
2. Каждая запись после последней старой групповой версии `1.0.17` получает отдельный последовательный номер: `1.0.18`…`1.0.999`, затем `1.1.0`. Существующие на момент перехода записи закреплены в неизменяемом `numbering-baseline.json`. Новые получают номера по first-parent порядку добавления в `main`, не по дате/имени файла. Поэтому PR со старой датой можно объединить позже, не сдвигая общие номера. После merge номер фиксирован; в неслитых ветках он предварительный. В списке видны дата и номер, последняя объединённая запись даёт актуальное описание web-обновления. Старые имена и фиксированную основу не переименовывают/переписывают. Перенос из `pending` в `released` сохраняет номера. Для общей публикации используйте полный Git-клон проверенного `main`, не неслитую feature-ветку.
3. Для выпуска EXE установить в `apps/desktop/package.json` и `apps/desktop/release-notes.json` текущий последний номер из списка обновлений. Проверить записи командой `pnpm check:release-notes`, собрать и опубликовать web/EXE, затем перенести выпущенные JSON-блоки из `release-notes/pending/` в `release-notes/released/<версия>/`. До фактической публикации переносить их нельзя. Обычный merge сам по себе не очищает `pending`. В описание выпуска для сервера попадают последние 50 пунктов (лимит API); вся предшествующая история остаётся в окне обновлений.
4. Подписать установщик сертификатом издателя, если сборка предназначена для реального распространения, и вручную проверить установку и вход на тестовом ПК. В распакованной сборке проверьте наличие `resources/app-update.yml`: Electron читает его даже при программной настройке адреса обновлений. Также проверьте, что политика соединений в собранном `dist/index.html` допускает точные HTTPS/WSS-адреса, заданные при сборке. Без первого файла проверка версии может пройти, но скачивание установщика не начнётся; без второго условия приложение не сможет проверить готовность сервера. Сервер проверяет SHA-512 и размер файла при публикации; это контроль целостности, **не замена цифровой подписи и теста установки**. Текущая внутренняя сборка без подписи может вызывать предупреждение Windows SmartScreen.
5. Суперадминистратор открывает профиль, загружает EXE, затем отдельно нажимает «Опубликовать». Обычный администратор не может загружать и публиковать сборки, но видит состояние уже опубликованного обновления.
6. После подтверждения, что клиенты скачивают и устанавливают опубликованную версию, администратор или суперадминистратор может нажать «Сделать обновление обязательным». Отключить блокировку можно там же. Сотрудники с установленной более старой версией получат экран загрузки и установки вместо рабочих разделов. Пока сервер или файл недоступны, этот экран не обходит блокировку — потому обязательный режим нельзя включать до проверки доступности.

Если уже выданный EXE не содержит `resources/app-update.yml`, он не сможет самостоятельно получить исправление. Оставьте обязательный режим выключенным, выдайте проверенный исправленный установщик для разовой ручной установки поверх прежней версии и только затем испытайте автоматическое обновление на одном тестовом ПК со следующей версией. Повторная публикация прежнего файла или повторная отправка запроса из клиента проблему не устранит.

Сервер в режиме `production` дополнительно отвергает обычные запросы устаревших клиентов кодом 426; пути получения обновления остаются доступны. Это предотвращает продолжение работы через старый EXE, который ещё не знает о новом экране. Поэтому **перед первым включением рубильника нужно один раз вручную установить клиент с автообновлением всем коллегам**: уже установленная прежняя версия не может получить новую функцию задним числом. В неproduction-режимах серверная проверка отключена, чтобы не запереть локальные тесты и браузер разработки.

Клиент проверяет политику сразу после входа, затем каждые 30 секунд и при событии сервера. Он скачивает установщик целиком (без дифференциального патча), проверяет контрольную сумму и предлагает установку. После перезапуска сотруднику нужно войти снова; приложение вернёт последний раздел. Черновики сообщений и формы новой задачи на этом ПК сохраняются через системное шифрование Electron. Как только черновик восстановлен в поле ввода, его локальный файл удаляется; новый ввод при необходимости создаст новый черновик. Неоткрытые файлы удаляются через 30 дней. Открытые модальные окна, прикреплённые, но не отправленные файлы, и произвольные незавершённые действия пока не восстанавливаются автоматически. Серверные сохранённые данные не затрагиваются.

В свободном режиме разные поддерживаемые версии клиентов могут работать одновременно: номер версии сам по себе не блокирует API. Поэтому изменения контрактов должны оставаться обратно совместимыми как минимум на период распространения обновления: новые поля ответа делаются необязательными для старого клиента, существующие поля и маршруты не удаляются в том же выпуске. Для web-версии пользователь может отложить напоминание на 30 минут, затем на 60, 90 минут и далее; новое опубликованное обязательное обновление игнорирует локальную отсрочку.

Максимальный размер загрузки по умолчанию — 350 МиБ (`YUKSALISH_UPDATE_MAX_BYTES`). Учитывайте свободное место сервера и одновременные загрузки по сети. Версии повышаются монотонно; откат требует отдельной новой версии, а не публикации старого номера.

Описание выпуска и EXE передаются в одном multipart-запросе: длинные пункты обновления больше не попадают в URL. Старый маршрут с описанием в query string и потоком `application/octet-stream` остаётся для уже установленных клиентов. Сначала обновите API, затем web/EXE. Внешний маршрут по-прежнему ограничен 90 МБ на запрос; установщик большего размера загружайте через офисный LAN, а не через публичный домен.

## Проверка перед рубильником

- `pnpm check:release-notes` проверяет уникальность и текст новых записей, сохранность истории и неизменность основы нумерации. Более ранняя дата новой записи не блокирует независимый PR. `pnpm test:workflow` проверяет оба порядка объединения, архивирование и предупреждения о пересечениях.
- Перед ручным `docker compose ... build web` или `up --build` запустите `scripts/lan/prepare-release-note-order.ps1` из корня полного Git-клона. Он создаёт игнорируемый `apps/desktop/release-notes/order.generated.json`: только SHA и порядок имён, без токенов и `.git`. Штатные deploy/restore делают это сами. После каждого изменения исходников/ревизии пересоздайте метаданные; в Docker/source archive сборка откажется продолжать с отсутствующим, неполным или несовпадающим SHA. Native Vite/EXE читает тот же порядок прямо из Git. Для архива исходников подготовьте метаданные **до** удаления `.git`; при обновлении архива не переносите устаревший файл порядка.
- Миграция применена, API запущен с постоянной директорией обновлений, внешний адрес HTTPS доступен с другого ПК.
- На одном тестовом ПК установлена предыдущая версия и проверено получение, скачивание, установка новой версии и повторный вход.
- Проверены неподписанная/подписанная сборка и предупреждения Windows именно в вашей среде.
- Загруженный файл доступен с сервера; есть резервная копия базы и каталога установщиков.
- Суперадминистратор готов немедленно выключить обязательный режим при сбое.

Локальная development-БД на рабочем ПК существует и содержит учётные записи. Это **не** подтверждает LAN-перенос или сквозной сценарий двух установленных версий: их следует проверить по [инструкции переноса](lan-server-transfer.md) перед использованием рубильника коллегами.
