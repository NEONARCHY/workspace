# Обновления Windows-приложения

Обновление хранится на собственном сервере Yuksalish, не собирается на ПК сотрудников и не подтягивается автоматически из GitHub. Разработчик собирает новую версию, проверяет её, затем суперадминистратор загружает установщик в «Профиль → Обновления приложения» и публикует. Только после публикации клиенты начинают скачивание. Отдельная кнопка включает или выключает блокировку устаревших версий.

## Перед первым запуском

1. Развернуть один сервер API и PostgreSQL. Применить Alembic-миграции, включая `0025_desktop_updates`. Миграция ограничивает число суперадминистраторов одним. Если такой пользователь уже есть, команда ниже не заменит и не повысит его автоматически — сначала проверьте учётные записи вручную.
2. Обеспечить постоянную директорию установщиков и резервировать её вместе с базой данных. В штатном Docker Compose используется том `desktop-updates` в `/workspace/var/desktop-updates`, а gateway разрешает потоковую загрузку до 350 МиБ. При запуске API вне Compose указать абсолютный путь через `YUKSALISH_UPDATE_DIRECTORY`, доступный для записи процессу API. Относительный путь `var/desktop-updates` подходит только для разработки.
3. Для ПК коллег предоставить API по постоянному адресу HTTPS с доверенным на каждом клиенте сертификатом. При сборке клиента установить `VITE_API_BASE_URL` в этот адрес, **без `/api/v1` и завершающего `/`**. Для переноса LAN-сервера см. [универсальную инструкцию](lan-server-transfer.md): адрес вида `https://192.168.1.50:8443` и внутренний корневой сертификат. Установщик, собранный с локальным `127.0.0.1`, не сможет получать обновления с другого компьютера. Обновления по незащищённому HTTP вне локального ПК клиент отвергает.
4. На серверном ПК, после миграции и до выдачи доступов, один раз запустить `yuksalish-provision-admins --superadmin-username baxtiyorsamugov --superadmin-name "Бахтиёр Самугов" --admin-username almazovtemur --admin-name "Темур Алмазов"` внутри окружения API. Команда запросит пароли дважды со скрытым вводом; не передавайте их аргументами, переменными окружения или через Git. Если учётные записи уже существуют, скрипт откажется менять роли/пароли. Включите TOTP при первом входе.

## Выпуск версии

1. При каждом push и в каждом Pull Request Codex добавляет собственный файл в `apps/desktop/release-notes/pending/` с уникальным `id` и 1–12 короткими пунктами на понятном пользователю языке. Разные PR не редактируют один общий список, поэтому при параллельном merge их тексты не затирают друг друга. CI блокирует push/PR без нового или обновлённого pending-блока.
2. Все pending-блоки автоматически объединяются по имени файла в один непрерывный список preview для web и EXE. Обычный merge не очищает этот список: он продолжает накапливаться, пока владелец вручную не решит опубликовать версию.
3. Для выпуска поднять номер `apps/desktop/package.json` по SemVer (`1.0.0`, `1.0.1`, `1.0.2`…) и указать тот же номер в `apps/desktop/release-notes.json`. Проверить итоговый longread командой `pnpm check:release-notes`, собрать и опубликовать web/EXE, затем перенести выпущенные JSON-блоки из `release-notes/pending/` в `release-notes/released/<версия>/`. До фактической публикации переносить их нельзя.
4. Подписать установщик сертификатом издателя, если сборка предназначена для реального распространения, и вручную проверить установку и вход на тестовом ПК. Сервер проверяет SHA-512 и размер файла при публикации; это контроль целостности, **не замена цифровой подписи и теста установки**. Текущая внутренняя сборка без подписи может вызывать предупреждение Windows SmartScreen.
5. Суперадминистратор открывает профиль, загружает EXE, затем отдельно нажимает «Опубликовать». Обычный администратор не видит этот раздел; API также отклоняет его запросы.
6. После подтверждения, что клиенты скачивают и устанавливают опубликованную версию, суперадминистратор может нажать «Сделать обновление обязательным». Отключить блокировку можно там же. Сотрудники с установленной более старой версией получат экран загрузки и установки вместо рабочих разделов. Пока сервер или файл недоступны, этот экран не обходит блокировку — потому обязательный режим нельзя включать до проверки доступности.

Сервер в режиме `production` дополнительно отвергает обычные запросы устаревших клиентов кодом 426; пути получения обновления остаются доступны. Это предотвращает продолжение работы через старый EXE, который ещё не знает о новом экране. Поэтому **перед первым включением рубильника нужно один раз вручную установить клиент с автообновлением всем коллегам**: уже установленная прежняя версия не может получить новую функцию задним числом. В неproduction-режимах серверная проверка отключена, чтобы не запереть локальные тесты и браузер разработки.

Клиент проверяет политику сразу после входа, затем каждые 30 секунд и при событии сервера. Он скачивает установщик целиком (без дифференциального патча), проверяет контрольную сумму и предлагает установку. После перезапуска сотруднику нужно войти снова; приложение вернёт последний раздел. Черновики сообщений и формы новой задачи на этом ПК сохраняются через системное шифрование Electron. Как только черновик восстановлен в поле ввода, его локальный файл удаляется; новый ввод при необходимости создаст новый черновик. Неоткрытые файлы удаляются через 30 дней. Открытые модальные окна, прикреплённые, но не отправленные файлы, и произвольные незавершённые действия пока не восстанавливаются автоматически. Серверные сохранённые данные не затрагиваются.

Максимальный размер загрузки по умолчанию — 350 МиБ (`YUKSALISH_UPDATE_MAX_BYTES`). Учитывайте свободное место сервера и одновременные загрузки по сети. Версии повышаются монотонно; откат требует отдельной новой версии, а не публикации старого номера.

## Проверка перед рубильником

- Миграция применена, API запущен с постоянной директорией обновлений, внешний адрес HTTPS доступен с другого ПК.
- На одном тестовом ПК установлена предыдущая версия и проверено получение, скачивание, установка новой версии и повторный вход.
- Проверены неподписанная/подписанная сборка и предупреждения Windows именно в вашей среде.
- Загруженный файл доступен с сервера; есть резервная копия базы и каталога установщиков.
- Суперадминистратор готов немедленно выключить обязательный режим при сбое.

Локальная development-БД на рабочем ПК существует и содержит учётные записи. Это **не** подтверждает LAN-перенос или сквозной сценарий двух установленных версий: их следует проверить по [инструкции переноса](lan-server-transfer.md) перед использованием рубильника коллегами.
