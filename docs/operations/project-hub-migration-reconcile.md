# Согласование веток миграций проекта и AI Referent

## Когда применять

Этот runbook относится только к серверу, на котором `alembic_version` содержит **ровно** `0055_project_hub`, проектные таблицы уже существуют, а новая версия кода ожидает цепочку `0054_ai_referent_operator_edit → 0055_ai_referent_preflight → 0056_project_hub`. Типичный симптом — API не запускается с `Can't locate revision identified by '0055_project_hub'`. Не пытайтесь лечить это повторным `docker compose up`: API сам запускает Alembic и снова упадёт.

Номер `0055_project_hub` был присвоен проектной миграции до появления другой миграции `0055_ai_referent_preflight` в общей ветке. В актуальном коде проектная миграция переименована в `0056_project_hub`. Менять только номер без проверки схемы нельзя: `stamp` не выполняет SQL-операции миграции.

## Сначала — восстановленная копия рабочей БД

1. Зафиксируйте точный commit сервера и состояние `git status`; незакоммиченные изменения не перезаписывайте. Остановите API, worker и scheduler; PostgreSQL, Redis и MinIO оставьте работающими. Сохраните и проверьте backup PostgreSQL, MinIO, `.env.lan` и Compose-конфигурации. Не используйте `down -v`, очистку volumes или команды пересоздания рабочей БД.
2. Восстановите PostgreSQL backup в **отдельную** БД/контейнер. Команды далее должны получать URL только этой копии. Зафиксируйте исходные `alembic_version`, количество строк в проектных таблицах, их структуру, индексы, ограничения и текущий head кода. Прекратите процедуру, если версия не ровно `0055_project_hub`, проектных таблиц не хватает, уже есть часть изменений preflight или схема отличается от ожидаемой `0056_project_hub`.
3. Сравните schema-only дамп таблиц `project_hub_*` **рабочей БД (только чтение)** и чистой тестовой БД, поднятой тем же актуальным commit до `0056_project_hub`. Исключите из сравнения только случайные строки `pg_dump` `\restrict`/`\unrestrict`; различия в таблицах, колонках, типах, FK, индексах или ограничениях — блокер. Затем сравните дамп восстановленной копии. `pg_restore` может иначе записать эквивалентные выражения `CHECK ... IN (...)`: это допустимо только после поимённой сверки каждого ограничения и его допустимых значений, при полном совпадении исходной рабочей схемы с чистой схемой. Все остальные различия остаются блокером. Отдельно проверьте ограничение `ck_workspace_notifications_section` и сохраните исходные SQL-результаты. При необходимости сравните тело применённого старого файла `0055_project_hub` с актуальным `0056_project_hub`: допустимо только изменение `revision`/`down_revision`.
4. Лишь на этой копии: `alembic stamp --purge 0054_ai_referent_operator_edit`, затем `alembic upgrade 0055_ai_referent_preflight`. Первый шаг **только переписывает указатель версии**: проектные таблицы остаются как были. Убедитесь, что preflight добавил ожидаемые колонки/таблицы и не изменил проектные записи.
5. Если структура проектов подтверждена, выполните `alembic stamp 0056_project_hub`, затем `alembic current` и `alembic upgrade head`. Ожидается ровно `0056_project_hub (head)`; последняя команда не должна делать DDL. Повторно сравните количество и контрольные выборки проектных строк, проверьте миграционный smoke-test, вход в API, проектные операции и AI Referent на копии.
6. Только после успешного прогона восстановленной копии согласуйте окно обслуживания. На рабочем сервере с новым проверенным backup повторите ту же последовательность и проверки, затем запустите API/worker/scheduler и проверьте readiness. Если любой шаг отличается — не запускайте сервисы и восстановитесь из проверенного backup; не продолжайте `stamp` наугад.

## Что уже проверено разработчиком

На **синтетической изолированной** PostgreSQL-БД, созданной старым `0055_project_hub`, проектная schema-only структура совпала с чистой схемой актуального `0056_project_hub` (кроме случайных строк дампа). Последовательность `stamp --purge 0054 → upgrade 0055_ai_referent_preflight → stamp 0056 → upgrade head` завершилась на `0056_project_hub (head)`; проектный интеграционный тест прошёл.

25.09.2026 создан и проверен свежий backup действующего сервера; его PostgreSQL-дамп восстановлен в отдельный контейнер с локальным портом. На момент копирования версия была ровно `0055_project_hub`, шесть проектных таблиц существовали и были пусты; признаков частичного применения `0055_ai_referent_preflight` не было. Schema-only дамп **исходной рабочей БД** совпал с чистой схемой `0056_project_hub` после исключения только `\restrict`/`\unrestrict`. После `pg_restore` шесть ограничений `CHECK ... IN (...)` были записаны PostgreSQL с другим синтаксисом приведения массива; имена, поля и допустимые значения совпали. На восстановленной копии последовательность согласования завершилась на `0056_project_hub (head)` без изменения количества проектных и AI Referent-записей. **На рабочей БД команды `stamp`/`upgrade` не выполнялись.** Перед применением на ней нужны свежая проверка CI, окно обслуживания и повторная проверка backup.
