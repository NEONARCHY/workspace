# Расширение чтения ЭДО: контракт для второго ПК

Версия соглашения: `incoming_read.version = 1`, 9 октября 2026.
Это задание для реализации серверной части ЭДО; текущий рабочий пилот ещё
не подтверждал поддержку этого расширения.

## Поведение

- Workspace admin/superadmin читают все входящие, карточки и разрешённые вложения.
- Назначенным владельцем руководителям Workspace выдаёт область всех писем
  либо писем текущих активных сотрудников выбранных подразделений плюс их
  собственные назначения.
- Обычный сотрудник видит личные назначения.
- Просмотр руководителем не меняет статус, версию, отметки просмотра,
  назначения, результат и журнал бизнес-переходов.
- Область чтения не даёт права передачи, выполнения или подтверждения.
  POST остаются закрытыми в текущем пилоте.
- Интерфейс, меню и формы прежнего ЭДО сохраняются.

## Доверие и утверждение

Bearer, HS256, issuer, audience, активность и TTL проверяются как в API v1.
`sub` всегда UUID фактического читателя Workspace. На каждом запросе ЭДО
проверяет его активное локальное сопоставление и отсутствие блокировки.
Нельзя использовать UUID уже сопоставленного исполнителя вместо администратора.
Нужны явные личные сопоставления администраторов и руководителей; не создавать
их по похожести имени и не переиспользовать чужое сопоставление.

Отсутствие `incoming_read` сохраняет API v1: только собственные назначения.
Расширенный GET несёт дополнительный **подписанный** claim:

```json
{
  "incoming_read": {
    "version": 1,
    "mode": "employees",
    "employee_ids": [
      "00000000-0000-4000-8000-000000000001",
      "00000000-0000-4000-8000-000000000002"
    ]
  }
}
```

Второй вариант: `{"version":1,"mode":"all","employee_ids":[]}`.
Workspace не передаёт расширенный claim для личного чтения или POST.

Сервер ЭДО принимает расширение только при отдельно включённой возможности
для доверенного issuer (предлагаемое новое имя настройки ЭДО:
`EDO_WORKSPACE_SCOPED_READ_ENABLED=1`; это **не существующая настройка**).
Пилотный allowlist читателей расширяется только согласованными UUID.
Присутствующий claim при выключенной возможности должен получить 403,
не молчаливое игнорирование.

Строго проверить типы, точные ключи, version=1, mode:
`employees` — 1–100 уникальных канонических UUID, в том числе sub;
`all` — пустой массив. Неизвестные ключи, modes, версии и неверные UUID — отказ.
Область нельзя читать из query, обычного неподписанного заголовка или тела запроса.
На изменяющем методе присутствующий `incoming_read` отвергается.

Workspace — источник правил и состава отделов. ЭДО доверяет области только
после проверки подписи доверенного Workspace; роль локального пользователя ЭДО
не используется как замена правилам Workspace. Для `employees` UUID
преобразуются в локальные ID через активные сопоставления **того же issuer**
и действующих пользователей ЭДО. Несопоставленные/отозванные целевые UUID
не дают доступа; неизвестный читатель по-прежнему получает 403.
Персональное сопоставление читателя можно отозвать немедленно в ЭДО.
Workspace пересчитывает область на каждом запросе; ранее выпущенное утверждение
может оставаться действительным до своего exp (Workspace выдаёт 120 секунд).

## Область выборки и подтверждение

Применить одну функцию авторизации ко всем трём GET:

1. Список: ограничение по назначениям применяется **до** COUNT, сортировки и
   LIMIT/OFFSET. Для employees — EXISTS назначение любому сопоставленному
   сотруднику области. Один документ выдаётся один раз при нескольких исполнителях.
2. Карточка: та же проверка, вне области — тот же 404, что для отсутствующего ID.
3. Файл: та же проверка письма до открытия файла плюс существующие проверки
   attachment_id, корня, расширения, ссылок/junctions и пути.
4. all возвращает весь реестр входящих, в том числе письма без назначенных
   исполнителей. Поиск и статус сужают разрешённый набор.

Успешные ответы расширенного GET (200, а также 206 для Range) возвращают
`X-Workspace-Read-Scope: <digest>`, Cache-Control no-store, private.
Digest — SHA-256 канонической JSON-строки проверенного claim, UTF-8/ASCII,
без пробелов, ключи строго `employee_ids`, `mode`, `version`,
employee_ids сортируются по возрастанию строк. Пример канонической all-строки:

```text
{"employee_ids":[],"mode":"all","version":1}
```

Для PHP 7.1 сформировать массив в этом порядке, отсортировать копию массива
UUID `sort($ids, SORT_STRING)`, затем `hash('sha256', json_encode($canonical))`.
Подтверждение добавляется только после применения области; нельзя просто
отражать клиентский заголовок. Workspace сравнивает digest перед обработкой
JSON/передачей байтов; отсутствие или несовпадение даёт 503.
Дополнительно Workspace проверяет пересечение назначений каждой карточки с
employees-областью. Список и метаданные ошибки не должны раскрывать чужие письма.

## Задание Codex на ПК ЭДО

Реализуй описанное расширение в отдельной ветке относительно текущего
подтверждённого серверного выпуска. Сохрани незакоммиченные изменения.
Добавь проверку claim в EmployeeAuthenticator и единый scope в чтение
MailWorkflow/Attachments. Сохраните прежнюю авторизацию записей и старого
веб-интерфейса. Если нужна новая схема — подготовь отдельную аддитивную миграцию;
не повторяй начальную миграцию интеграции.

Проверь на синтетических данных: admin all; руководитель employees; обычный
личный доступ; несколько исполнителей без дублей; правильные total и пагинация;
чужая карточка/файл 404; неподписанный scope не влияет; неверные claims отказ;
отзыв сопоставления; неизвестные целевые UUID не расширяют выдачу; claim
не разрешает POST; чтение не меняет документ. Проверь checksum на том же примере,
совместимость PHP 7.1 и проксирование нового response header.

Верни коммит, тесты и статус готовности. Не расширяй рабочий allowlist, не меняй
реальные письма и не открывай запись автоматически. После проверки обеих сторон
в согласованном выпуске включается расширенное чтение.

## Workspace: выпуск и откат

Сначала совместимый сервер ЭДО с выключенным расширением; затем выбранная
миграция Workspace `0081_edo_incoming_access`, API и web/desktop.
Убедиться, что текущий Alembic head совместим, без параллельных неприменённых веток.
Для открытия реестра администраторам на ЭДО должны быть подготовлены их
индивидуальные сопоставления и включён scoped-read capability.

Проверить в Workspace: all admin/superadmin; руководитель с одним отделом;
смена отдела/блокировка сотрудника; отзыв правила; отдельное скачивание;
назначенный исполнитель и наблюдающий руководитель; ответ старого API без ack.
Не объявлять расширенный доступ работающим по одним тестам Workspace.

Откат: закрыть scoped-read на ЭДО, сохранив личный пилот, и при необходимости
вернуть совместимую версию Workspace. Правила/аудит оставить в БД.
Не выполнять down на рабочей БД ради отката кода. Глобальная блокировка POST
пилота сохраняется. Существующие ограничения старых прямых ссылок ЭДО и
неподтверждённого часового пояса этим расширением не меняются.
