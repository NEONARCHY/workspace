# Обновление перед презентацией 6 октября 2026

Эта инструкция относится к уже настроенному серверу с `.env.lan` и двумя
Compose-файлами из репозитория. Для другой схемы запуска сначала используйте её
runbook; не заменяйте офисные адреса и секреты значениями тестового ПК.

## Что входит

Общий PR #93 уже находится в `main`. Новый PR личной эффективности добавляет
серверный запрос и интерфейс без новой миграции. Но при обновлении с версии
**до #93** должны примениться предыдущие миграции, включая
`0072_chat_avatar_icons` → `0073_project_hub_chats` → `0074_sidebar_visibility` →
`0075_assistant_chats`. API в Compose применяет Alembic при запуске автоматически.
Старые маршруты сохранены. Не запускайте demo seed на существующем сервере.

## Бахтиёру: обновление существующего LAN-сайта

1. Сначала сохранить резервную копию базы и пользовательских файлов/томов по
   действующему runbook. Проверить свободное место, рабочую `.env.lan`, доверенный
   сертификат, отсутствие чужих незакоммиченных изменений (`git status`).
   Git не переносит базу, секреты или файлы между ПК.
2. Запустить Docker Desktop и дождаться, пока `docker info` перестанет выдавать
   ошибку. Открыть PowerShell **в папке проекта на серверном ПК**.
3. После merge нового PR выполнить:

   ```powershell
   git switch main
   git pull --ff-only origin main
   .\scripts\lan\deploy-web.ps1 -EnvFile .env.lan
   ```

   Скрипт проверяет настройки, пересобирает API и web, запускает сайт,
   перечитывает gateway и проверяет готовность. Нужно дождаться сообщения
   `Yuksalish Web is healthy`, не только окончания `pull`.
4. Сверить состояние и текущую миграцию:

   ```powershell
   docker compose --env-file .env.lan -f infrastructure/compose.yaml -f infrastructure/compose.lan.yaml ps -a
   docker compose --env-file .env.lan -f infrastructure/compose.yaml -f infrastructure/compose.lan.yaml exec -T api alembic -c apps/api/alembic.ini current
   ```

   Ожидается `0075_assistant_chats (head)` и работающие сервисы. На **адресе своего
   сервера** открыть `/version.json` и `/api/v1/health/ready`: версия соответствует
   новому выпуску, готовность возвращает 200. В браузере принять обновление или
   нажать Ctrl+F5. На этом тестовом ПК адрес — `https://192.168.31.176:8443/`;
   это не предполагаемый адрес офисного сервера.
5. До презентации проверить вход обычного сотрудника и администратора, задачи,
   собственный профиль → «Моя эффективность», приглашение, проекты, чат
   ассистента и старую переписку. При ошибке смотреть `logs --tail 100 api`;
   не публиковать логи с токенами/личными данными. Не включать обязательное
   обновление EXE до проверки одного реального клиентского ПК.

## Если Docker завис, а код уже обновлён

После перезапуска Docker достаточно повторить `deploy-web.ps1` из шага 3.
Повторять `pull` нужно, только если появились новые коммиты. Один `docker restart`
запустит **старый образ**, а не соберёт новый код. Если ошибка повторяется,
сначала проверить `docker info`, `ps -a` и логи, не удалять данные.

**Не использовать `docker compose down -v`, удаление томов, сброс базы или
`docker system prune --volumes`.** Docker хранит там данные сайта.

## Если показываете установленное Windows-приложение

Обновление сайта не меняет уже установленный EXE. Нужна отдельная сборка,
проверка и установка/публикация клиента с офисным API-адресом по
[инструкции обновлений](desktop-updates.md). Для браузерной демонстрации EXE
пересобирать не требуется. Сквозной тест офисного клиента остаётся обязательным:
зелёный CI не гарантирует правильный IP, сертификат, доступность Docker или
настройки конкретного ПК.
