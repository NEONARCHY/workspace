# Один сервер Yuksalish в локальной сети — передача Бахтиёру

Это инструкция для первого LAN-пилота. На ПК Бахтиёра работают Docker, API, PostgreSQL,
Redis, MinIO и локальный HTTPS-вход. На остальных ПК работает только установленный desktop.
Интернет-маршрут, Cloudflare и проброс портов роутера **не включаются**.

```text
ПК сотрудников ── HTTPS https://<LAN-IP-Бахтиёра>:8443 ── Caddy ── gateway ── API
                                                               ├── PostgreSQL
                                                               ├── Redis
                                                               └── MinIO
```

Установщики по LAN не проходят через лимиты Cloudflare. Единственная открытая в LAN
служба — HTTPS-порт 8443; gateway остаётся на `127.0.0.1:8080` серверного ПК,
PostgreSQL — на его `127.0.0.1:55432`, Redis и MinIO не опубликованы. Серверный
ПК должен быть включён, подключён по Ethernet, не уходить в сон и иметь резервную копию
вне собственного диска. Docker Desktop может запускаться при **входе пользователя** в
Windows, но это не гарантирует работу сразу после перезагрузки без входа.

## Передача кода и решение о данных

1. Сначала влить зависимую ветку с автообновлением и эту LAN-ветку через PR в `main`
   после зелёного CI. `git pull` не переносит БД, вложения, секреты и EXE.
2. Текущий локальный сервер — `development` с `YUKSALISH_SEED_DEMO_DATA=true`. В нём
   сейчас 7 учётных записей и Alembic `0025_desktop_updates`; часть записей может быть
   тестовой. Перед доступом сотрудников владелец и Бахтиёр должны просмотреть их и
   заблокировать/архивировать тестовые аккаунты. Скрипты ничего не удаляют.
3. Если нужно сохранить текущие задачи, чаты, пользователей и файлы, используйте
   экспорт ниже. Если решено начать с пустой базы, не запускайте восстановление и
   создайте первого администратора по `docs/operations/environments.md`; это **другой**
   сценарий и старые учётные записи в нём не появятся.

## Что делает владелец на нынешнем серверном ПК

Подготовить зашифрованный внешний диск (BitLocker или эквивалент), свободное место и
папку-родитель, например `E:\`. Не использовать Git, облачный чат или обычную флешку
для базы и вложений. Перед окончательным экспортом попросить всех прекратить работу.

В PowerShell из корня репозитория выполнить безопасную проверку:

```powershell
.\scripts\lan\export-handoff.ps1 -BackupDirectory 'E:\Yuksalish-Handoff-2026-09-14' -PreflightOnly
```

Если проверка успешна, выполнить экспорт. Он попросит набрать `CUTOVER`, остановит
текущие сервисы записи, сделает логический дамп PostgreSQL и копии томов MinIO, Redis,
обновлений. Источник **останется выключенным**, чтобы не возникли две расходящиеся базы.
Папка назначения должна быть новой; существующие данные скрипт не перезапишет.

```powershell
.\scripts\lan\export-handoff.ps1 -BackupDirectory 'E:\Yuksalish-Handoff-2026-09-14' -ConfirmCutover
```

Проверить наличие `manifest.json`, `database.dump` и трёх `*.tar.gz`; оставить исходные
Docker-тома на месте для отката. Секретный `.env` с нынешнего development-сервера **не
копировать** на ПК Бахтиёра: он содержит тестовые значения. Если экспорт оборвался,
не продолжать с неполной папкой и не создавать ещё один сервер; сначала выяснить причину.

## Что делает Бахтиёр на своём ПК

1. Установить Docker Desktop, Git, Node.js и pnpm по `README.md`, получить слитый
   `main`: `git switch main; git pull --ff-only origin main`. ПК должен иметь достаточно
   места для БД, файлов, обновлений и резервных копий. Зафиксировать его IPv4 в DHCP
   роутера — ниже вместо примера `192.168.1.50` использовать **фактический** адрес.
   Сеть Windows должна быть `Private`.
2. Не запускать Yuksalish Compose до восстановления. Если на его ПК уже есть проект
   `yuksalish-workspace` или одноимённые Docker-тома, восстановление откажется их
   трогать. Ничего не удалять автоматически; сначала проверить, нет ли там важных данных.
3. Получить зашифрованный диск, разблокировать и из корня репозитория создать новый
   локальный файл конфигурации. Скрипт генерирует новые случайные пароли и ключи,
   сохраняет исходное имя бакета и **не показывает секреты в терминале**:

```powershell
.\scripts\lan\new-server-environment.ps1 -ServerIp '192.168.1.50' -BackupDirectory 'E:\Yuksalish-Handoff-2026-09-14'
.\scripts\lan\restore-handoff.ps1 -BackupDirectory 'E:\Yuksalish-Handoff-2026-09-14' -PreflightOnly
```

   `.env.lan` исключён из Git. Скрипт использует новые auth-ключи, потому что на
   проверенном источнике нет **подтверждённых** TOTP-факторов. Старые сессии могут
   потребовать повторного входа. Если к моменту реального экспорта подтверждённая
   двухфакторная защита появится, экспорт остановится: смену ключа надо планировать
   отдельно, иначе код подтверждения перестанет работать.
4. После успешной проверки выполнить восстановление и набрать `RESTORE`:

```powershell
.\scripts\lan\restore-handoff.ps1 -BackupDirectory 'E:\Yuksalish-Handoff-2026-09-14' -ConfirmEmptyTarget
```

   Восстановление **только в пустой Compose-проект**. Оно проверяет SHA-256 всех файлов,
   восстанавливает тома и БД, сверяет число пользователей, затем запускает API и
   применяет новые миграции. При ошибке не запускать скрипт повторно поверх созданных
   томов и не включать старый сервер одновременно — сначала разобрать состояние.

## Открыть доступ только в локальной сети

На ПК Бахтиёра от имени администратора Windows создать одно входящее правило.
Заменить адрес и подсеть на реальные; пример `/24` годится **только** если именно
такую подсеть показывает роутер. Не создавать port forwarding на роутере.

```powershell
New-NetFirewallRule -DisplayName 'Yuksalish LAN HTTPS' -Direction Inbound `
  -Action Allow -Protocol TCP -LocalPort 8443 -LocalAddress '192.168.1.50' `
  -RemoteAddress '192.168.1.0/24' -Profile Private
```

На ПК Бахтиёра включить в Docker Desktop `Settings → General → Start Docker Desktop
when you sign in`, затем проверить после перезагрузки и входа в Windows. Отключить
сон при питании от сети. Настроить отдельную внешнюю зашифрованную резервную копию
и проверить восстановление до использования с реальными сотрудниками.

## Сертификат и первый установщик

Сертификат Caddy внутренний: он бесплатный, но его **корневому сертификату** надо
доверять на каждом рабочем ПК. Корневой приватный ключ остаётся на сервере в томе
`yuksalish-workspace_lan-caddy-data`; его нельзя выдавать сотрудникам. Если том
утрачен, сертификат изменится и доверие на всех клиентах придётся устанавливать заново.

Бахтиёр экспортирует **только публичный** корневой сертификат на съёмный носитель:

```powershell
.\scripts\lan\export-root-certificate.ps1 -DestinationFile 'E:\Yuksalish-LAN-root.crt'
```

Сверить показанный SHA-256 лично или по независимому каналу. На каждом ПК сотрудника
запустить `trust-root-certificate.ps1` (его можно скопировать вместе с `.crt`, без
репозитория), подставив реальный отпечаток. Скрипт доверяет CA только для текущего
Windows-пользователя, не для всех учётных записей компьютера:

```powershell
.\trust-root-certificate.ps1 -CertificateFile '.\Yuksalish-LAN-root.crt' -ExpectedSha256 '<64-символьный-SHA-256>'
```

Проверить с **другого** ПК, что `https://192.168.1.50:8443/api/v1/health/ready`
открывается без ошибки сертификата. Не отключать проверку TLS и не нажимать
«Продолжить, несмотря на предупреждение».

Владелец или Бахтиёр после merge и `pnpm check` собирает Windows-установщик с тем же
адресом. Скрипт откажется собирать, если HTTPS/доверие к сертификату не работает:

```powershell
.\scripts\lan\build-installer.ps1 -ServerIp '192.168.1.50'
```

Этот EXE один раз установить вручную на ПК владельца, Бахтиёра и тестового
сотрудника. Старые установщики с `127.0.0.1:8080` не могут сами переключиться на
общий сервер. Входить существующими аккаунтами из перенесённой БД. Проверить чаты,
вложения, задачи, права, повторное открытие desktop и обновление на двух ПК.

Для каждого следующего выпуска: PR → зелёный CI → merge → `git pull` на серверном
ПК → `docker compose --env-file .env.lan -f infrastructure/compose.yaml -f
infrastructure/compose.lan.yaml up -d --build --wait` при установленном в PowerShell
`$env:YUKSALISH_ENV_FILE='../.env.lan'` → новая версия EXE → тест установки →
загрузка и публикация у суперадминистратора → только затем обязательный режим.
`merge` сам по себе не обновляет сервер, БД или установленные приложения.

## Проверка, откат и ограничения

- До первого входа/изменения данных на новом сервере можно остановить его и поднять
  старый источник из сохранённых томов. После появления новых записей на ПК Бахтиёра
  **нельзя** просто включить старый сервер: данные разойдутся. Нужен отдельный перенос
  в обратную сторону.
- Не включать обязательное обновление, пока предыдущая версия EXE не установлена на
  тестовом клиенте и не прошла весь путь обновления по LAN. Текущие неупакованные
  тесты этого не доказывают.
- Приложение доступно только в той же подсети. При гостевой Wi-Fi-сети, изоляции
  клиентов или другой VLAN потребуется отдельное сетевое правило, не открытие
  PostgreSQL/MinIO.
- Локальный Caddy CA — временное решение для LAN. При будущем интернет-доступе нужен
  отдельный дизайн TLS/адреса и новый bootstrap-установщик; существующий LAN-EXE
  привязан к LAN IP.
- Сменить пароли тестовых/демо-учётных записей и включить TOTP для администратора
  после успешного переноса. Никогда не размещать `.env.lan`, дамп, вложения или EXE в Git.

Основание для HTTPS и доверия на клиентских ПК: [Caddy local HTTPS](https://caddyserver.com/docs/automatic-https).
Автозапуск Docker Desktop зависит от входа в Windows: [Docker Desktop settings](https://docs.docker.com/desktop/settings-and-maintenance/settings/).
