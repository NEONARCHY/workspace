# 1С → проекты: подготовка пилота

## Состояние первого этапа

Проверка 26.11.2026 для предоставленной владельцем базы:

- веб-вход работает; «Бухгалтерия для Узбекистана», редакция 3.0, расширение Yuksalish;
- стандартный OData доступен по HTTPS: без авторизации HTTP 401, с авторизацией HTTP 200;
- в ответе `$metadata` есть пустой `EntityContainer`, нет ни одного `EntitySet`;
- для проверенной учётной записи нет доступного состава объектов. По этому ответу
  нельзя различить пустой общий состав публикации и ограничения конкретного пользователя;
- транзакции не читались, состав публикации и права не менялись, импорт не включён.

XML и отчёты сохранены отдельно от Git. В исходниках нет рабочего адреса, логина,
пароля или финансовых данных. Это диагностический этап, не работающая синхронизация.

## Задание специалисту 1С

1. Проверить существующий состав стандартного OData и права отдельного служебного
   пользователя. Публикация интерфейса уже отвечает: переустанавливать сервер ради этого
   не требуется. Не заменять прежний состав вслепую — могут существовать другие потребители.
2. Вместе с бухгалтером указать точный признак проекта в этой конфигурации/расширении:
   отдельный справочник, договор, субконто, дополнительный реквизит либо иной разрез.
   Название проекта и текст назначения платежа не являются надёжным ключом сопоставления.
3. Согласовать один проект и один закрытый месяц. Подготовить контрольный отчёт:
   поступления, перечисленные деньги, признанные расходы, возвраты и начальные остатки
   по проекту, организации и каждой валюте. Оплата аванса и признание расхода различаются.
4. Определить минимальный набор объектов и реквизитов, из которых получается этот отчёт:
   ключи/коды проектной аналитики, документы поступлений и оплат, бухгалтерские движения,
   нужные статьи и валюты, состояние проведения/пометки удаления, изменения и сторно.
   Названия объектов нельзя брать из другой типовой конфигурации без проверки этой базы.
5. Добавить согласованные объекты в состав OData и дать служебному пользователю только
   необходимое чтение. Состав публикации и запрет записи — отдельные настройки;
   публикация только нужных объектов сама по себе не запрещает POST/PATCH/DELETE.
6. Передать имена доступных наборов, описание аналитики и контрольный отчёт оператору
   Workspace. Секрет служебного пользователя передаётся отдельно, не через Git или PR.

Если бухгалтерские агрегаты/разрезы нельзя достоверно получить через OData, согласовать
узкий HTTP-сервис чтения с теми же контрольными цифрами. Не включать весь состав базы.

Официальная документация: [публикация и состав OData](https://kb.1ci.com/1C_Enterprise_Platform/FAQ/Development/Integration/How_to_use_the_oData_protocol_when_publishing_an_infobase_to_web_server/),
[HTTP-сервисы](https://1c-dn.com/1c_enterprise/http_services/).

## Повторная проверка со стороны Workspace

Из собственной рабочей копии, Python 3.11 с зависимостями проекта:

```powershell
$env:YUKSALISH_ONEC_BASE_URL = 'https://one-c.example/Infobase/'
$env:YUKSALISH_ONEC_USERNAME = 'service-account'
python scripts/operations/onec_preflight.py --output 'C:/Private/onec-report.json'
```

Ввести пароль в скрытом приглашении. Он не сохраняется. При автоматизированном
запуске допустим секрет окружения `YUKSALISH_ONEC_PASSWORD`; не передавать пароль
аргументом командной строки и не добавлять его в Vite/renderer.

Для анонимной диагностики использовать `--anonymous` без настроенного имени пользователя.
Флаг `--empty-password` допускается только для явно согласованной разовой проверки
существующего входа без пароля; он не является настройкой фонового обмена.

`--metadata-output 'C:/Private/onec-metadata.xml'` дополнительно сохраняет только XML-схему.
Отчёты могут раскрывать структуру учёта: хранить отдельно от исходников и не коммитить.
Существующие файлы не перезаписываются. В консоль выводится только краткий результат.

| Результат | Значение |
|---|---|
| `available` | Прочитана непустая схема; это ещё не проверка финансовых сумм |
| `authentication_required` / 401 | Вход в OData не принят; автоматического перебора нет |
| `access_denied` / 403 | Требуется проверка прав в 1С |
| `odata_not_found` / 404 | Указанный путь стандартного OData не найден |
| `no_published_objects` / 200 | В этой выдаче нет наборов данных; проверить состав и права |
| `invalid_metadata` | Вместо ожидаемой схемы получены другие или небезопасные данные |
| `timeout` / `connection_failed` | Ошибка соединения, не пустой финансовый результат |

Код завершения 0 означает только успешное обнаружение схемы. Код 2 означает блокировку
проверки, включая пустой состав при HTTP 200. TLS-проверка включена; перенаправления
запрещены, чтобы не передать авторизацию другому адресу. Клиент отправляет только GET
к `$metadata`, ограничивает размер ответа и закрывает соединения после проверки.

## Следующий этап и критерии включения

После получения доступной схемы адаптер строится по подтверждённым объектам этой базы.
Далее необходимы сопоставление стабильных идентификаторов проектов и бюджетных статей,
пробная загрузка без записи, сверка с контрольным отчётом, обработка исправлений/сторно,
повторных запусков и явная отметка свежести данных.

Фактические показатели 1С нельзя прибавлять к текущим расходам Workspace: завершённая
заявка уже может присутствовать в `project_payment_expenses`. Требуется связь заявки
и бухгалтерского документа, отдельное происхождение сумм и проверка отсутствия дублей.
План, денежные выплаты и признанные расходы — разные показатели. Валюты не складываются
без согласованного курса и даты; точные суммы не преобразуются в float.

Чтение финансовых данных в UI должно наследовать серверный доступ к проекту, включая
выключенный режим администратора. Показатели не должны раскрывать недоступные документы.
Ошибка обновления сохраняет последнюю успешную сверенную версию с отметкой устаревания.

Изменения API/БД и фоновые задания ещё не реализованы и не развёрнуты. Выпуск пилота
потребует отдельной проверки миграций и тестового сервера. Офисный сервер не обновлялся.
