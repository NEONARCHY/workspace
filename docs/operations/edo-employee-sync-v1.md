# Синхронизация сотрудников Workspace с ЭДО

Workspace передаёт свой каталог сотрудников в ЭДО. Подтверждённые личные привязки
сохраняются; для непривязанного UUID ЭДО создаёт обычную интеграционную учётную
запись. Это отдельная серверная возможность, а не разрешение записи писем.
Интерфейс прежнего ЭДО, назначения и статусы писем не меняются.

Реализация Workspace готовит задания и отправляет их только после включения
настройки. Для рабочего подключения необходим описанный ниже маршрут ЭДО.

## Владение данными

- Ключ личности — `(issuer Workspace, employee_id UUID)`, не ФИО, email или логин.
- Если уже есть подтверждённое сопоставление, сохранить его `edo_user_id`.
  Не создавать дубль, не менять логин, пароль и права существующего аккаунта.
- Без сопоставления создать отдельного пользователя ЭДО с детерминированным
  логином `ws_<32 lowercase UUID hex>`. Нельзя автоматически привязывать похожие
  имена: спорный старый аккаунт остаётся нетронутым.
- Новому аккаунту назначить минимальную обычную роль. Не переносить роль
  администратора Workspace. Прямой вход в старый ЭДО не включать автоматически:
  не копировать пароль, не генерировать доступный пользователю пароль и не
  отправлять письма активации. Запись нужна для назначений и API.
- Хранить имя, подразделение и должность как управляемые Workspace метаданные.
  Для интеграционно созданных аккаунтов разрешено обновлять отображаемое имя
  и должность. Для прежних аккаунтов обновлять метаданные сопоставления, не
  перезаписывать профиль старого ЭДО.
- Если старой схеме обязателен email, использовать уникальный технический адрес
  `ws-<UUID hex>@workspace.invalid`, без исходящей почты; не выдавать его за
  настоящий email сотрудника. Сначала проверить ограничения фактической схемы.

| Статус Workspace | Действие ЭДО | mapping_active |
| --- | --- | --- |
| active | Создать или обновить личную запись и активировать сопоставление | true |
| pending | Создать запись ожидания, доступ API пока закрыт | false |
| blocked, archived, disabled | Деактивировать сопоставление; не создавать отсутствующий аккаунт | false |

Деактивация не удаляет пользователя, назначения или историю. У прежнего аккаунта
ЭДО не менять права прямого входа из-за статуса Workspace. Личное чтение остаётся
ограниченным назначениями; полный просмотр определяется отдельной подписанной
областью чтения. Новый сотрудник не получает полный просмотр от синхронизации.

## Запрос

`PUT /workspace/v1/employees/{employee_id}` — новый серверный маршрут ЭДО.
UUID в URL и теле должны совпадать. Только JSON, разумный предел тела 16 KiB,
неизвестные ключи и неправильные типы отклонять. Формат полей — snake_case.

```json
{
  "protocol_version": 1,
  "employee_id": "00000000-0000-4000-8000-000000000001",
  "revision": 1,
  "username": "synthetic_employee",
  "full_name": "Тестовый сотрудник",
  "status": "active",
  "department_id": null,
  "department_name": null,
  "job_title": null
}
```

`revision` — положительный целочисленный номер снимка данного UUID. `username`
1–64, `full_name` 1–200, `department_name` до 200, `job_title` до 160 символов.
UUID канонические; поля подразделения и должности допускают null.
Имя подразделения — метаданные, не автоматическое создание/изменение структуры
старого ЭДО. Пароли, роли, письма и права просмотра не входят в этот запрос.
Неподдерживаемые кодировкой имена отклонять, не сохранять искажённую строку.

## Отдельная авторизация

Настройки Workspace, по умолчанию выключенные:

- `YUKSALISH_EDO_EMPLOYEE_SYNC_ENABLED=false`;
- `YUKSALISH_EDO_DIRECTORY_CREDENTIAL` — отдельный случайный bearer минимум 32 символа;
- `YUKSALISH_EDO_DIRECTORY_ASSERTION_KEY_BASE64` — отдельный ключ HS256 минимум 32 байта;
- существующие `YUKSALISH_EDO_API_URL`, `YUKSALISH_EDO_WORKSPACE_ID`,
  `YUKSALISH_EDO_CA_BUNDLE` задают origin, issuer и доверие TLS.

Нельзя переиспользовать credential или ключ чтения писем. Секреты хранятся только
на серверах и передаются защищённым каналом, не в чате, Git или renderer.

ЭДО должен добавить отдельный флаг и отдельные настройки directory bearer hash
и signing key. Их фактические имена фиксируются в отчёте реализации ЭДО;
существующие read credentials не расширяются. Проверять bearer и подпись вместе,
issuer, HS256, audience, subject, срок жизни до 120 секунд и допустимое отклонение
часов до 30 секунд. `alg=none`, иной алгоритм и неизвестные claims отклонять.

Заголовки запроса:

- `Authorization: Bearer <directory credential>`;
- `X-Workspace-Directory-Assertion: <JWT>`;
- `Idempotency-Key: employee:<UUID>:v<revision>:<первые 16 hex SHA-256 тела>`.

Подписанные claims:

```json
{
  "iss": "yuksalish-workspace",
  "aud": "edo-directory-sync-v1",
  "sub": "workspace-directory-sync",
  "iat": 1000,
  "exp": 1120,
  "operation": "employee.sync",
  "employee_id": "00000000-0000-4000-8000-000000000001",
  "revision": 1,
  "method": "PUT",
  "path": "/workspace/v1/employees/00000000-0000-4000-8000-000000000001",
  "payload_sha256": "<64 lowercase hex>"
}
```

Digest вычислять по **исходным байтам HTTP-тела**, не по повторной JSON-сериализации.
Workspace отправляет ASCII JSON с Unicode escape, сортировкой ключей и без
пробелов между элементами. Подпись относится к фактическому методу, пути,
UUID, revision и digest тела. Проверить связь каждого claim с запросом.
Сравнивать секреты и подписи безопасным constant-time способом.

Directory credential не даёт доступа к письмам. Credential чтения и обычная
сессия ЭДО не дают доступа к этому PUT. Шлюз разрешает только данный PUT через
отдельную проверку; остальные изменяющие методы писем и method override остаются
закрытыми. Для созданной активной личной привязки согласованно разрешать чтение
на шлюзе по проверенному issuer/UUID, не открывать wildcard для неизвестных UUID.

## Транзакция и подтверждение

ЭДО хранит уникальный ключ `(issuer, employee_id)`, последнюю revision, digest,
remote user ID и подтверждение. Создание пользователя, сопоставление, журнал
и запись результата идемпотентности выполняются в одной транзакции.
Первое создание сериализовать уникальным ключом и блокировкой; повтор при
гонке должен найти уже созданную запись, не создавать второго пользователя.

- Меньшая revision — `409`, никаких изменений.
- Равная revision с тем же digest — прежнее успешное подтверждение, без
  повторной записи и побочных эффектов.
- Равная revision с другим digest — `409`, никаких изменений.
- Большая revision — обновление управляемого снимка и новое подтверждение.
- Повторный Idempotency-Key с другим телом — `409`.
- Блокировка native аккаунта ЭДО имеет приоритет: не снимать её синхронизацией;
  вернуть `409` и оставить сопоставление недействующим до ручного согласования.

Успех `200` либо `201` содержит только:

```json
{
  "protocol_version": 1,
  "employee_id": "00000000-0000-4000-8000-000000000001",
  "revision": 1,
  "request_sha256": "<64 lowercase hex SHA-256 полученного тела>",
  "edo_user_id": 101,
  "mapping_active": true,
  "action": "created"
}
```

`action`: created, linked, updated, unchanged или absent. Для blocked/archived/
disabled без существующего пользователя `action=absent`, `edo_user_id=null`,
`mapping_active=false`. Для active/pending требуется положительный числовой
`edo_user_id`. Передать ранее сохранённое подтверждение при идентичном повторе.
Смена подтверждённого remote ID — конфликт, не автоматическое перепривязывание.

## Очередь Workspace

Миграция `0083_edo_employee_sync` хранит последнее задание каждого сотрудника.
Фоновая сверка выполняется каждые 20 секунд между пакетами до 20 запросов.
Она охватывает существующих, импортированных и будущих сотрудников; изменение
имени, отдела, должности и статуса создаёт новую revision. При недоступности
ЭДО доставка задерживается; это не атомарная общая транзакция двух систем.

HTTP идёт вне транзакции PostgreSQL. Lease 120 секунд предотвращает одновременную
доставку; запрос ограничен 55 секундами. После перезапуска lease истечёт и тот же
снимок повторится. Старый ответ не отмечает новый снимок доставленным.
Ответ 408/425/429/5xx и сетевой сбой повторяются с задержкой до часа;
403/404/409 требуют проверки администратором. Сохраняется код ошибки, не тело ответа.
После временной ошибки пакет прекращается; следующий цикл сначала сверяет
свежие данные каталога, а не ждёт тайм-аутов всего пакета.

В «Входящие письма → Доступ к письмам» администратор раскрывает «Синхронизация
сотрудников с ЭДО»: состояния, ID ЭДО и повтор ошибочного задания.
Ручной повтор ставит в очередь, а не объявляет синхронизацию успешной.
GET `/api/v1/incoming-letters/employee-sync` и POST
`/api/v1/incoming-letters/employee-sync/{UUID}/retry` требуют роль admin/superadmin
и модульное право incoming_letters.admin. Аудит доставки и ручного повтора атомарен.

## Проверки и включение

1. На ПК ЭДО реализовать контракт в отдельной ветке, сохранив грязный checkout
   и существующие 18 сопоставлений. Старую миграцию повторно не запускать.
   Если нужны новые поля revision/digest/idempotency, добавить отдельную миграцию.
2. На отдельной БД проверить сохранение прежних ID, UUID нового сотрудника,
   pending→active→blocked→active, archived без создания аккаунта, повтор после
   потерянного ответа, конкуренцию создания и устаревшую revision. Проверить
   отказ credentials другой возможности и подменённого тела/пути/метода.
3. Подтвердить неизменность старого интерфейса, писем и закрытых POST;
   проверить чтение собственных назначений новой личности без полного доступа.
4. Согласованно выпустить ЭДО с directory flag выключенным; передать отдельные
   credentials защищённо. Выпустить Workspace с миграцией 0083 и flag=false.
5. Из API-контейнера Workspace проверить TLS и тестовый UUID. После подтверждения
   включить обе стороны и сверить 18 существующих привязок и очередь остальных.
   Установщик EXE для серверной синхронизации не требуется.

Отключение флага Workspace прекращает новые циклы, текущий запрос может завершиться.
Для немедленного запрета отключить directory endpoint на ЭДО. Не удалять учётные
записи, назначения, delivery state и журнал при откате. Восстановление старой БД
Workspace может уменьшить revision: ЭДО обязан отказать 409, затем требуется
согласование версий, а не принудительная перезапись.
Менять issuer или переносить настройку на другой экземпляр ЭДО без проверки
сопоставлений и очереди нельзя. Доверие CA и проверка имени TLS остаются включены.

## Задание для второго ПК

Реализуй серверный маршрут employee sync v1 строго по этому контракту. Сохрани
существующие личные сопоставления, интерфейс ЭДО, рабочие незакоммиченные изменения
и закрытую запись писем. Никакой привязки по похожим ФИО и никакого копирования
паролей или административных ролей. Проверь фактические ограничения таблиц,
создай отдельные directory credentials и необходимые новые миграции, не повторяя
старые. По умолчанию функция выключена. Прогони контрактные и конкурентные тесты;
дай точные имена настроек, версию коммита и порядок согласованного включения.
Секреты в чат не выводи. Рабочее включение и изменение настроек шлюза — отдельный
согласованный этап после проверки из API-контейнера Workspace.
