# Эффективность сотрудников — правила EFF-1

Статус: реализовано в desktop 0.18.0 / API 0.15.0. Методика: EFF-1.0. Дата: 2026-09-07.

## Запрос

Каждый сотрудник видит свой показатель, общие показатели коллег и уведомления об изменениях собственной эффективности. В интерфейсе есть объяснение простыми словами: что учитывается, как считается, как улучшить результат и каких действий избегать. Референс — предоставленный экран Bitrix; оформление остаётся Yuksalish/Gilroy.

## Подтверждённые ограничения текущего кода

- `tasks` хранит текущие `status`, `due_at`, `primary_assignee_user_id`, `updated_at`, но не отдельное время завершения, сдачи на проверку и полную историю изменений срока/исполнителя.
- Изменение статуса обновляет `updated_at`; последующее редактирование карточки тоже его обновляет. Использовать `updated_at` как дату завершения нельзя.
- `task_comments` — обычные комментарии. Их количество не является количеством ошибок или замечаний.
- Статусы `awaiting_review`, `completed`, `in_progress` существуют, но переход назад не содержит обязательной причины. Нельзя автоматически считать его доказательством плохого качества работы.
- Задачи ограничены существующими правами автора, исполнителя, участников и руководителей. Доступ к показателям коллег не должен расширять доступ к самим задачам, комментариям и вложениям.
- Уже есть серверная очередь уведомлений с уникальным ключом события, отметками чтения/доставки и пользовательскими настройками. Эффективность должна использовать её, а не отдельные повторяющиеся всплывающие окна.

## Основной показатель

Название в интерфейсе: **«Выполнение задач в срок»**, внутри раздела «Эффективность». Это характеристика исполнения зарегистрированных задач, не универсальная оценка ценности сотрудника или качества работы.

Процент своевременно выполненных задач; возвраты к работе и просрочки показываются отдельными числами с пояснением, без скрытых штрафных коэффициентов. Все учитываемые задачи имеют одинаковый вес. Пример: 8 своевременных результатов из 10 задач, попавших в расчёт, — 80%.

### Правила для утверждения вместе с основной формулой

1. Период — календарный месяц в Asia/Tashkent; текущий месяц считается только по уже наступившим срокам. Будущие сроки не превращаются в невыполнение. Показывать количество задач в расчёте рядом с процентом.
2. Задачи без срока показывать отдельно; они не снижают процент. При нулевом знаменателе — «Нет данных», не 0% и не 100%. Предупреждать о малой выборке.
3. Для сдачи на проверку учитывать своевременную отправку результата, не задержку руководителя. Нужен отдельный учёт отправки, принятия и мотивированного возврата.
4. Перенос срока до его наступления должен быть виден в истории. Перенос после просрочки не должен стирать факт пропуска прежнего срока. Смена исполнителя после просрочки не должна автоматически переносить чужую просрочку на нового сотрудника.
5. Отменённые задачи, ожидание внешних зависимостей и изменение требований требуют явного объяснения исключения. Не выдавать произвольное изменение статуса за подтверждённое основание для штрафа или освобождения от расчёта.
6. Исторические события начать записывать с внедрения. Старые завершения и переносы не восстанавливать по догадке; явно отметить неполную историю. График не должен рисовать выдуманные прошлые значения.
7. Показывать прозрачную методику и её версию. Не использовать показатель автоматически для зарплаты, штрафов, увольнения, ограничения доступа или публичных ярлыков «плохой сотрудник».

## Интерфейс

- В разделе «Задачи» — вкладка «Эффективность», рядом со списком и Kanban.
- Сводка «Моя эффективность»: процент или отсутствие данных, числитель/знаменатель, выполнено, просрочено, ожидает проверки, без срока.
- Общая таблица сотрудников с поиском: имя, должность, числовые показатели, объём данных. По умолчанию — нейтральный порядок по имени, не публичная доска «худших».
- При выборе сотрудника — его общая сводка; конкретные задачи показываются только при существующем праве доступа. Агрегат не должен отдавать скрытые названия или идентификаторы задач в API.
- «Как считается»: формула, пример на числах, исключения, дата начала учёта и ограничения. «Как улучшить»: реалистичные сроки, раннее сообщение о препятствиях, своевременная передача результата на проверку. «Чего избегать»: задачи без ясного результата, задние переносы сроков, фиктивное закрытие, дробление работы ради количества.
- График — только из реальных событий/снимков. Изменения доступны также текстом; Gilroy, фирменная палитра, reduced motion, таблица при узком окне прокручивается внутри контейнера.

## Уведомления

- О собственном приближении срока, наступившей просрочке, мотивированном возврате и изменении своего показателя с причиной; без дублирования уже имеющихся напоминаний по задачам.
- Дневная/недельная сводка вместо сообщения при каждом пересчёте; повторная проверка сервера не создаёт дубликатов.
- Сохранение внутренней истории и отдельная настройка всплывающих уведомлений. Существующие настройки и право их отключить сохраняются.
- Не рассылать всем персональные ухудшения коллег по умолчанию. Общая таблица доступна, но дополнительные подписки на чужие показатели требуют отдельного решения.

## Реализация и критерии приёмки

- EFF-1A: неизменяемый серверный журнал событий задачи, начальный снимок существующих задач без выдуманной истории и версия методики EFF-1.0.
- EFF-1B: серверный расчёт агрегатов, личный/общий экран и полная доступная справка. Период, часовой пояс, числитель/знаменатель и дата начала достоверного учёта явные.
- EFF-1C: мотивированный возврат, подтверждённое исключение, дневные сводки и дедупликация через существующую очередь уведомлений.
- EFF-1D: 77 Python/PostgreSQL-тестов с покрытием 82,12%, 121 UI-тест, типизация, линт и installer 0.18.0. SHA-256 установщика: `2800CB7976DB91A1A7961DF861011142E07A3B61C5D4D3954474DD46326DAAE6`; внутренняя сборка без цифровой подписи.

API эффективности отдаёт только агрегаты сотрудников. Идентификаторы, названия, комментарии, файлы и проекты закрытых задач в ответ не включаются; существующие права просмотра карточек не расширяются. График строится только при наличии минимум двух реальных периодов, а прежние месяцы явно помечаются как неполные или недоступные.
