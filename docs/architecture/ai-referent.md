# AI Referent: общий реестр входящих и исходящих писем

AI Referent объединяет исходящие письма Workspace/Telegram и входящие письма,
зарегистрированные Windows-роботом на ПК референта. PostgreSQL является общим источником
для интерфейса Workspace. Локальная SQLite робота пока остаётся источником автоматизации
входящих и передаёт в Workspace идемпотентные снимки через защищённый bridge.

## Граница первого релиза

Первый вертикальный сценарий включает:

- создание и редактирование черновика в Workspace;
- загрузку файла через общий защищённый механизм вложений;
- выбор согласующего;
- согласование или возврат с обязательной причиной;
- атомарную выдачу номера формата `0001/26-AI`;
- постановку согласованного письма в идемпотентную очередь доставки;
- единый журнал событий и системный аудит;
- модульные права `view`, `create`, `edit`, `approve`, `admin`.

Этот релиз намеренно не забирает команду из очереди и физически не отправляет письмо.
До подключения агента статус `queued` означает «готово для безопасной доставки», а не
«отправлено». Адаптер общих согласующих описан ниже; физическая доставка писем
через очередь Workspace пока не подключена.

Входящий сценарий добавляет табличный реестр, идемпотентный batch endpoint агента,
исходные номера и даты, организацию, тему, ответственного, срочность, сведения о
вложениях, статус обработки и последнюю версию `register.xlsx`. Bridge читает SQLite
робота в read-only режиме и не меняет его базу или Excel. Архивы писем и сами вложения
пока не передаются. Следующий этап должен синхронизировать файловые пакеты из
существующих каталогов робота без обязательного переноса архива вручную.

## Состояния

```text
draft / needs_revision
        -> pending_review
        -> approved
        -> queued
        -> sending
        -> sent

pending_review -> needs_revision
queued/sending -> failed -> queued
любое незавершённое состояние автора -> cancelled
```

Номер присваивается только при согласовании. Счётчик хранится отдельно по двухзначному
году и изменяется в той же транзакции, поэтому два одновременных согласования не могут
получить один номер. Каждый запрос изменения передаёт `expectedRevision`; устаревший
клиент получает HTTP 409 и обязан перечитать запись.

## Доступ

- Администратор видит все письма.
- Обычный сотрудник видит созданные им письма, письма на его согласовании и уже
  отправленные записи общего реестра.
- Черновик редактирует автор или администратор.
- Согласовать, вернуть, поставить в очередь или повторить отправку может назначенный
  согласующий с правом `approve` либо администратор.
- Проверки выполняются сервером; скрытие кнопки в desktop не является барьером.
- Входящий реестр читают пользователи с правом `ai_referent.view`.
- Запись входящих и Excel-журнала принимает только служебный endpoint с отдельным
  `YUKSALISH_AI_REFERENT_AGENT_TOKEN`.

## Данные и вложения

- `ai_referent_letters` — текущая карточка и её revision;
- `ai_referent_number_counters` — последовательность номеров по году;
- `ai_referent_events` — читаемая история действий;
- `ai_referent_delivery_commands` — команды доставки с idempotency key и lease-полями;
- `workspace_attachments` с owner type `ai_referent_letter` — файлы писем в MinIO.
- `ai_referent_incoming_letters` — входящие записи робота с уникальной парой
  `agent_id + external_id`;
- `ai_referent_agents` — heartbeat агента и метаданные последнего Excel-журнала;
- объект `ai-referent/journals/<agent>/...xlsx` в MinIO — скачиваемый снимок журнала.

Миграции: `0044_ai_referent`, `0045_ai_referent_incoming`, `0046_ai_referent_reviewers`.
После развёртывания API
необходимо выполнить обычный
`alembic upgrade head` до запуска новой версии desktop.

Ответственный сохраняется как внешний ID/имя робота и как nullable
`responsible_user_id`. До регистрации реальных сотрудников интерфейс показывает
исходное имя с пометкой «Ожидает сопоставления». Позже Бобура, Умида, Аскара и Даврона
можно связать с реальными логинами без потери истории.

## Общие согласующие

Четыре стабильные роли `askar`, `bobur`, `umid`, `davronbek` связываются с UUID
аккаунта Workspace и числовым Telegram ID. Должность не используется для назначения.
`ai_referent_configuration` хранит revision, `ai_referent_reviewers` — привязки;
`ai_referent_letters.reviewer_key` удерживает роль при замене человека. Открытые
письма переназначаются в той же транзакции; история завершённых решений не меняется.

Записывать конфигурацию может только admin/superadmin с обычной пользовательской
авторизацией. Агентский ключ позволяет читать настройки и подтверждать применение,
но не менять пользователей/права. Каждый редактор передаёт `expectedRevision`.
API использует блокировку конфигурации для согласованного чтения и сериализации
переназначений с действиями над письмами. Явный запрет модуля и неактивный аккаунт
учитываются и в данных, передаваемых боту.

Канонический адаптер: `integrations/exat/workspace_integration`; установщик:
`scripts/install_exat_workspace.py`. Адаптер обновляет назначения работающего бота
между операциями, не перезапуская процесс посередине отправки. Это общая конфигурация,
а не синхронизация жизненного цикла писем: исходящие операции Exat ещё используют
его локальную БД. [Установка и ограничения](../operations/ai-referent-reviewers.md).

## Следующий этап: общий цикл писем, файлы и доставка

1. Перевести исходящий Telegram-сценарий на API AI Referent: создать черновик, загрузить
   файл, отправить на согласование и читать тот же реестр.
2. Использовать служебную аутентификацию агента и добавить endpoints claim/heartbeat/
   complete/fail для `ai_referent_delivery_commands`.
3. Запускать Exat-agent только в интерактивной Windows-сессии. Он получает одну команду,
   использует существующий адаптер E-XAT или webmail и подтверждает результат в API.
4. Синхронизировать существующие входящие/исходящие и файловые пакеты из каталогов
   робота, сохраняя номера и исключая дубли; показать пакеты в Workspace.
5. Сохранить локальные каталоги и SQLite робота для его автоматизации, но исключить
   два независимых источника решений: общий API должен атомарно принимать каждое
   решение и доставлять уведомления в Workspace и Telegram через outbox.
6. Проверить весь действующий цикл Exat: предварительный и финальный согласующие,
   комментарии, повторная подача, подпись, ручная отправка референтом и ошибки доставки.

Такая последовательность позволяет развернуть PostgreSQL на другом сервере без смены
бизнес-модели: desktop, бот и агент меняют только адрес API, а не обмениваются файлами
базы между собой.
