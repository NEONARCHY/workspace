# Отпуска

С октября 2026 новые заявления о ежегодном трудовом отпуске проходят отдельный
модуль `leave_approvals`. Исторические записи `absences` не мигрируют и остаются
доступными в «Отсутствиях». В форме нового отсутствия отпуск больше не предлагается.

Маршрут: действующий сотрудник пишет свободный текст заявления и указывает
предполагаемое начало (окончание — необязательно). Отправка из его аккаунта
фиксируется в истории; рисовать подпись не нужно. Система сохраняет неизменяемый
PDF заявления с местом для резолюции. Его исходные данные и каждый новый PDF
хранятся отдельно, по хешу проверяются перед выдачей и открываются встроенным
просмотрщиком только участникам и администраторам.
Шапка примера, текстового предпросмотра и PDF адресована первому заместителю
председателя — исполнительному директору по действующему маршруту; имя адресата,
должность и имя автора подставляются из учётных данных, а не вводятся в текст аризы.

Рядом с полем заявления сотрудник может раскрыть вымышленный пример аризы по
бумажному образцу. Просмотр не подставляет текст и не меняет черновик; отдельная
кнопка явно вставляет короткую фразу. Даты и данные автора в итоговом PDF берутся
из формы и аккаунта, без рукописной подписи.

Назначенный в HR кадровик проверяет заявление и **вручную** вводит окончательные
даты отпуска, рабочий период, число календарных и оплачиваемых дней, дату выхода,
номер приказа и ФИО/должности для печати. Номер резервируется в реестре по году
кадровой проверки; дубликат отвергается уникальным индексом. При смене года до
подписания заместитель возвращает заявку кадрам для нового номера. Кадровик
может вернуть заявление автору с причиной или отклонить его.

Кадровик может исправить текст и предполагаемые даты заявления до передачи
заместителю. Это создаёт новую версию PDF с отметкой об авторе кадровой правки,
сохраняет отдельное действие в истории и уведомляет автора; не подменяет его
аккаунт или подпись. Автор по-прежнему
может исправлять заявление на этапе кадров и после возврата.

Дополнительные дни считаются **только от даты приёма в организацию**, указанной
в HR-профиле сотрудника, а не от общего стажа. По умолчанию после полных 5/10/15
лет и следующего дня доступны соответственно 2/4/6 дней. Назначенный кадровик
может изменить возрастающие пороги в разделе отпусков. В конкретной заявке он
выбирает 0 или допустимое число дней; API независимо проверяет стаж на дату
начала отпуска. Снимок даты приёма и число дополнительных дней сохраняются в
заявке. «Календарных дней» — общий итог с допднями, количество оплачиваемых
дней кадровик вводит отдельно.

До передачи заместителю кадровик может править три текстовых пункта проекта
приказа и открывать неподписанный PDF из несохранённой формы. При передаче
тексты пунктов фиксируются в заявке; заместитель видит именно их и подписывает
тот же вариант приказа. Пустой пункт формируется по образцу автоматически.

После кадровой проверки утверждать может только единственный активный обладатель
должности `Rais birinchi o‘rinbosari – ijrochi direktor`. Он видит неподписанный
проект приказа, может вернуть его кадрам или отклонить с причиной. При
утверждении сервер проверяет личную подпись этого заместителя, создаёт и
регистрирует итоговый PDF с фирменной шапкой и тремя пунктами из присланного
образца. До этого момента подпись **никогда** не входит в предпросмотр. Сотрудник
и кадровик получают уведомления; решение и актёр сохраняются в аудите.

Интервалы новых заявлений не должны пересекаться друг с другом, действующими
отсутствиями или утверждёнными поездками. Утверждённый отпуск участвует в сводке
присутствия как `vacation`; в обратную сторону новые отсутствия проверяются на
пересечение с отпуском. Администратор имеет общий доступ к модулю; права
принимать кадровое решение и подписывать приказ дополнительно проверяются по
назначенному пользователю на сервере, а не только по роли модуля.

Обновление: сначала миграции отпуска, включая
`0106_leave_tenure_order_draft`, и API, затем desktop/web.
Старый desktop может продолжать работать: его порядок меню сервер дополняет
новым ключом, сохраняя персональный порядок остальных разделов. Рабочие данные
не копируются из старого модуля. Тесты документов используют только вымышленные
имена и подписи.

### Проверки перед запуском (19.10.2026)

Правка кадровиком проверяет пересечения для автора заявления, а не для кадровика.
После правки действие кадровой проверки остаётся в уведомлениях; сотрудник получает
информационное уведомление с отдельной атрибуцией исправления.

Новые клиенты передают `expectedUpdatedAt` при редактировании, кадровом решении,
предпросмотре приказа и решении заместителя. Сервер отклоняет устаревшую редакцию
с 409. Редактор сохраняет исходную версию формы даже после обновления списка.
Поле необязательное для совместимости, поэтому для этой защиты нужно обновить
web/desktop вместе с API. Число дней для расчёта не может превышать календарные
дни, а календарные дни — включительный период отпуска. Выходные/исключаемые дни
не выдумываются: кадровик по-прежнему вводит обоснованные значения вручную.

Все операции, резервирующие период сотрудника (отпуск, отсутствие, утверждение
поездки), используют общую транзакционную блокировку. Сравнения поездок и
отпусков включают обе даты; datetime-отсутствие использует полуоткрытый интервал
в часовом поясе Ташкента. Порог стажа для 29 февраля в невисокосный год —
28 февраля, дополнительные дни доступны со следующего дня после порога.

Перед организационным запуском необходимо проверить **на целевом сервере**:

- Единственного активного первого заместителя и назначенного активного кадровика.
- Личную подпись заместителя: загрузка только из его аккаунта, без замены подписью председателя.
- Дату приёма в организацию в HR-профиле каждого сотрудника, претендующего на допдни.
- Точное написание должностей и ФИО в реквизитах приказа; автотранслитерация имён
  в отпускных документах не подменяет кадровые данные.
- Совпадение API и клиента, миграции до `0107_trip_cleanup_actions`, резервную копию
  перед обновлением и доступ к хранилищу документов.

Воспроизводимые проверки: `test_travel_leave_launch_postgres.py`,
`test_leave_workflow_postgres.py`, `test_leave_tenure_rules.py`,
`scripts/qa/travel-leave-pdf-smoke.py` (нужен Poppler) и
`scripts/qa/travel-leave-ui-smoke.cjs` с Vite на 127.0.0.1:5176.
UI-стенд `qa/travel-leave-launch.html` блокирует бизнес-запросы и содержит только
синтетические данные; он не доказывает работу авторизации установленного EXE.
