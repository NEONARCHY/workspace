# Входящие письма ЭДО в Workspace

## Граница систем

ЭДО остаётся источником истины для письма, статуса, исполнителей, результата и файлов.
Новый раздел «Входящие письма» обращается к ЭДО только через сервер Workspace.
Браузер и Electron не получают служебный credential или ключ подписи. Данные ЭДО
не копируются в PostgreSQL Workspace. Миграция расширенной видимости хранит
только правила доступа; исходный личный пилот отдельной миграции не требовал.
Существующая вкладка «Входящие» AI Referent остаётся независимым реестром робота.
Совпадение писем между двумя источниками нельзя выводить из номера; устойчивый
идентификатор ЭДО — пара `(экземпляр ЭДО, mails_incoming.id)`.

Основа контракта — предоставленный владельцем `WORKSPACE_API.md` от 8 октября 2026 года,
ветка ЭДО `codex/workspace-server-integration`, коммит `32e0860`. Наличие кода, результаты
его тестов и рабочая схема ЭДО независимо на этом ПК не проверялись.

## Маршрут запроса и полномочия

1. Workspace проверяет сессию действующего сотрудника и модульное право
   `incoming_letters.view` либо `incoming_letters.edit`.
2. Сервер выпускает утверждение HS256 с неизменяемым UUID сотрудника, `iss`, `aud`,
   `active=true` и сроком 120 секунд. Отдельный служебный credential и утверждение
   отправляются только по проверяемому HTTPS к фиксированному адресу ЭДО.
3. ЭДО проверяет своё активное сопоставление сотрудника, назначение на конкретное
   письмо и допустимость действия. Служебный credential сам по себе доступа не даёт.
4. Два POST передают `expected_version` и новый `Idempotency-Key`. Workspace не
   повторяет запись автоматически после таймаута/обрыва. Пользователь сначала
   перечитывает карточку. `409` требует обновления версии.

В исходном контракте список и карточка доступны только назначенному исполнителю.
Расширение чтения для администраторов и руководителей описано ниже. Любой текущий
исполнитель открытого письма вправе добавить следующего; первоначальный остаётся
назначенным. Один исполнитель может отметить **всё письмо** выполненным (`2`).
Подтверждение (`3`) остаётся отдельным действием старого веб-интерфейса ЭДО.
Результат выполнения необязателен и ограничен 255 символами. Пустой ввод
не передаётся как очистка прежнего результата.

Workspace показывает краткое описание из `description`. Полного текста в этом поле
нет; оригинал открывается из защищённого вложения, PDF можно просмотреть в карточке.
Скачивание идёт через сервер с повторной проверкой прав, без прямого статического
URL ЭДО. API ЭДО v1 не выдаёт историю действий и не поддерживает поиск по организации
или фильтр просрочки: интерфейс честно ограничивает поиск номером и описанием.

## Сроки

Исторические даты ЭДО приходят без подтверждённого часового пояса. Пока
`YUKSALISH_EDO_LEGACY_TIMEZONE` пуст, раздел показывает сами сроки, но не объявляет
открытое письмо просроченным. После сверки фактического часового пояса с владельцем
ЭДО настройка принимает IANA-зону; просрочка для открытых писем определяется по
правилу старого списка ЭДО: календарная дата `deadline` раньше текущей даты этой
зоны. `deadline2` показывается отдельно и не подменяет `deadline`.

## Конфигурация и безопасный выпуск

Настройки сервера Workspace: `YUKSALISH_EDO_API_URL` (только HTTPS-origin),
`YUKSALISH_EDO_SERVICE_CREDENTIAL`, `YUKSALISH_EDO_ASSERTION_KEY_BASE64`,
`YUKSALISH_EDO_WORKSPACE_ID` и, после проверки сроков, `YUKSALISH_EDO_LEGACY_TIMEZONE`.
Для собственного CA допустим `YUKSALISH_EDO_CA_BUNDLE` с публичным сертификатом,
доступным внутри API-контейнера. Проверку TLS отключать нельзя. Пустые настройки
оставляют шлюз выключенным и возвращают понятную ошибку; секреты не пишутся в Git.

До рабочего включения необходимо:

1. Проверить текущую DDL ЭДО, миграцию `m261008_130000_workspace_integration.php` на
   обезличенной копии, резервную копию и план обработки частичного MySQL DDL.
2. Выпустить код и миграцию ЭДО согласованно, затем настроить отдельные credentials,
   HTTPS/proxy и активные сопоставления только пилотных сотрудников. UI ЭДО не меняется.
3. Проверить прямые старые URL вложений и закрыть этот обход прав до объявления
   файлового архива защищённым. Проверить часовой пояс и фактические типы полей.
4. Настроить HTTPS-доступ API-контейнера Workspace к ЭДО без публикации MySQL;
   включить значения только в серверных `.env` и выполнить пилот на тестовом письме.
5. Сверить список, карточку, PDF, передачу, выполнение, `2 → 3` в ЭДО,
   конфликт версии и разрыв связи. Только после этого расширять доступ сотрудникам.

В ЭДО v1 нет маршрута истории и потока изменений. Раздел читает актуальное состояние
при открытии/обновлении, а не обещает мгновенную фоновую синхронизацию. Старый
способ редактирования и любые прямые SQL-писатели ЭДО требуют отдельной проверки.

## Расширенная видимость, 9 октября 2026

Миграция Workspace `0081_edo_incoming_access` добавляет только правила доступа,
не копирует письма. Администратор и суперадминистратор получают режим `all`.
Для остальных по умолчанию `assigned`; администратор может явно выбрать
`departments` с 1–20 существующими подразделениями либо `all`.
Выбранные отделы учитываются точно, без автоматического включения дочерних.
В режиме подразделений сервер при каждом запросе вычисляет UUID действующих
сотрудников этих отделов и добавляет текущего читателя. Переводы/деактивации
учитываются в следующих запросах. Историческую принадлежность письма отделу
это правило не восстанавливает. Максимум — 100 UUID вместе с читателем;
превышение возвращает ошибку, список не обрезается.

GET `/api/v1/incoming-letters/access` возвращает правила активных сотрудников и
справочник подразделений. PUT `/access/{user_id}` принимает `expectedRevision`,
`mode`, `departmentIds`. Оба действия требуют роль admin/superadmin и
`incoming_letters.admin`. Модульного права без роли недостаточно. Правила
администраторов заблокированы для редактирования. Запись и аудит
`edo.incoming_visibility_updated` атомарны; устаревшая ревизия даёт 409.

Список, карточка и скачивание вычисляют одну область на сервере и передают её
в подписанном утверждении исходного сотрудника. Подмена читателя исполнителем
не используется. Дополнительная область разрешает только чтение. POST сохраняют
прежнее утверждение и права назначенного исполнителя. На главной
`personal=true` сужает список до личных назначений до пагинации.

Краткие строки списка ЭДО v1 не содержат назначений. Их область и пагинацию
обеспечивает ЭДО; Workspace проверяет digest подтверждения области, не
отбрасывает строки без исполнителей и не пересчитывает total локально.
Дополнительная проверка назначений выполняется для полной карточки и перед
скачиванием вложения в режиме подразделений.

**Необходима отдельная доработка API ЭДО.** До её выпуска расширенные запросы
завершаются понятной ошибкой, если ЭДО не подтвердил применение области.
Личный пилот старого контракта совместим. Точный контракт, проверки и задание
для второго ПК: [EDO read scope v1](../operations/edo-read-scope-v1.md).
Включение рабочего расширенного доступа и запись в ЭДО этой веткой не выполняются.
