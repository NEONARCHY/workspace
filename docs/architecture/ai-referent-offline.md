# AI Referent: автономная работа Telegram-бота

## Цель и граница текущего пакета

Цель — продолжать создание, согласование, подготовку и разрешённую внешнюю отправку
писем при потере Workspace, затем восстановить в нём файлы, решения, историю,
комментарии и голосовые сообщения без повторного внешнего действия. Время догоняющей
синхронизации зависит от количества и размера файлов; гарантия «за одну секунду»
невозможна. Подтверждённые владельцем правила: при аварии бот использует последнюю
проверенную копию Telegram-прав; внешняя отправка допускается только с заранее
зарезервированными номерами; AI Referent в доступном, но отрезанном от бота Workspace
переходит в режим просмотра.

**Текущий пакет ещё не пригоден для производственного автономного режима.** Локальный журнал
`offline_journal.py` устойчиво хранит операции, файлы по SHA-256, снимки по
Telegram ID и квитанции начала внешнего действия. Бот умеет показывать ранее
полученные с сервера списки/карточки и скачивать уже сохранённые на ПК файлы,
когда API недоступен. Это не гарантия полноты: фоновая загрузка может не успеть
до аварии, а файл больше 50 МБ не помещается в текущий лимит загрузки.
На текущем этапе локальный исполнитель также может подготовить подписанный PDF
из автономно согласованного письма, а сервер — принять его и историю подготовки
без повторного задания. Бот адресно доставляет PDF и текущую стадию Бобуру,
автору и, на стадии референта, администратору; текстовый/голосовой возврат
доставляется автору и воспроизводится на сервере. После возврата маршрут снова
начинается с первого согласующего, ранее присвоенный номер сохраняется.
Финальное подписание без отправки покрыто отдельными PDF-страницами. Локальная
отправка E-XAT/Webmail записывает на диск начало действия непосредственно перед
физическим кликом. Если процесс падает или исход неизвестен, повторный клик
заблокирован до ручной сверки внешнего журнала. Уже взятые сервером задания во
время аварии требуют отдельной проверки перед выпуском режима.
Входящие обновления Telegram теперь записываются в SQLite с синхронной записью
на диск до продвижения offset и до обработки; после перезапуска незавершённые
обновления сначала берутся из этого журнала. Для ряда изменяющих запросов
применяется постоянный ID, но сообщение в чате всё ещё может продублироваться при аварии между
отправкой ответа в Telegram и отметкой обработки.
Сервер теперь умеет атомарно выдавать назначенному агенту идемпотентные диапазоны
номеров через `POST /ai-referent/agent/offline/number-reservations`; отдельная
миграция сохраняет происхождение каждого диапазона. Локальный журнал умеет
запрашивать диапазон с постоянным ID, сохранять ответ и выдавать номер только
один раз на письмо. Локальный шлюз автономной записи требует серверную эпоху,
ждёт полный срок аренды и дополнительный запас по монотонным часам; после
перезапуска он повторно ждёт полный срок сохранённой аренды, а старые записи
без сохранённого срока остаются заблокированы. Уже подтверждённый
переход в офлайн хранится на диске. Неизвестная или подтверждённая отправка
блокирует новую попытку по письму, даже с другим ID или каналом. Только
подтверждённая человеком недоставка допускает новую попытку с новым ID. Эти
средства используются локальными обработчиками бота, но флаг выпуска выключен. Сервер также может выдать
назначенному роботу список реально разрешённых Telegram ID только в рамках
живой эпохи и сохраняет неизменяемую копию с её ID для последующей сверки.
Повтор запроса с тем же ID возвращает именно прежнюю копию, даже если права
за это время изменились или аренда истекла. Локальный журнал записывает ID
запроса до обращения к серверу и использует его после перезапуска; ответ с
неизвестным ID не принимает. Он проверяет контрольную сумму и заменяет копию
целиком, поэтому отзыв ID не оставляет его в прежней копии. Копия включает
разрешённые действия в AI Referent. Локальный журнал может атомарно связать
будущую автономную операцию с эпохой, ID копии прав и её SHA-256; старые записи
без такого доказательства не допускаются к автоматическому воспроизведению.
При воспроизведении сервер повторно проверяет конкретное письмо, стадию и
требуемое действие по сохранённой копии прав. Если
повторный ответ содержит устаревший формат прав, запрос можно отклонить с
сохранением причины и создать новый ID. Подготовлен координатор, который
продлевает аренду, обновляет копию прав и резерв номеров, а при обрыве связи
переходит в офлайн только после истечения серверной аренды и при наличии
проверенных прав. После возвращения сервера он требует сверки журнала. Этот
координатор подключён к рабочему циклу бота: после запуска прежней синхронизации
он продлевает аренду в отдельном потоке даже во время долгого задания, а в
режимах офлайн и сверки не запускает серверные задания. Обработчики Telegram
переключают черновики, документы, комментарии и базовые решения на локальный движок
 только при подтверждённой автономной фазе. Пакет письма в этот период выдаёт только
 файлы, физически сохранённые в локальном журнале; серверные вложения без локальных
 байтов недоступны. Независимый от продления аренды фоновый поток постепенно
 сохраняет весь доступный справочник адресатов по страницам, страницы
 активных/отправленных писем, полные карточки,
 опубликованные голосовые замечания и файлы пакетов отдельно для каждого
 разрешённого Telegram ID. Байты пакетов проверяются по размеру и SHA-256 до
 записи, а перед выдачей проверяются повторно. Для исторического аудио сервер
 отдаёт размер без хеша: локальный хеш рассчитывается после загрузки и
 проверяется при чтении. Администраторам поток
 сохраняет только отдельный список
 этапов чужих писем: содержимое и действия по ним остаются закрытыми. В офлайне
 это заведомо неполная и устаревающая копия; запрос, ответивший уже после смены
 эпохи, фазы или проверенных прав, не записывается. Поиск адресатов работает по
 локальной копии только после загрузки всех её страниц; неполный справочник не
 выдаётся за полный. Готовность всех архивных файлов к моменту аварии пока не
 гарантирована: предварительная загрузка идёт в фоне.
 Сервер может принять
файл автономного журнала по SHA-256 в изолированное хранилище без публикации в письме;
повтор того же файла безопасен. Локальная подготовка выбирает только файлы, на
которые ссылаются ещё не подтверждённые операции. Приёмка доступна лишь назначенному
роботу в его эпохе и только при включённом флаге автономного режима. Передача
подписанного PDF, результата внешней отправки и подтверждение подготовки
подключены к циклу сверки. Сервер принимает результат без повторного физического
действия и проверяет подпись, источник решения, номер, права и квитанцию.
Автоматическая выдача резерва в живом процессе подготовлена координатором.
Полный переход обратно к общему режиму пока не признан готовым к выпуску.
Не разворачивать этот пакет как выполнение всей задачи.

Первый вертикальный шаг воспроизведения теперь принимает создание и изменение
автономного черновика, вложения, результат проверки подписи, голосовой комментарий
и решения «на согласование», «одобрить», «вернуть» и «отменить».
Сервер проверяет
SHA-256 файла повторно, назначенного агента, эпоху, сохранённую
копию прав, автора, детерминированный ID письма и сквозной порядок журнала.
Изменения письма, файл и квитанция фиксируются одной транзакцией; события
создания и редактирования сохраняют исходное время.
Повтор той же операции возвращает квитанцию; иной запрос с тем же ID отвергается.
Голосовая запись проходит повторную проверку Opus, автора, назначенного согласующего,
версии письма и SHA-256. Решение повторно сверяется со стадией, маршрутом и
подтверждёнными правами на момент автономной работы. Для финального одобрения
исходящий номер должен входить в заранее выданный агенту резерв и не быть
занятым другим письмом. Сервер создаёт задачу подготовки только один раз после
подтверждения решения и принимает подписанный PDF по SHA-256 вместе с итогом
автономной подготовки. При доработке тот же номер сохраняется, а маршрут
согласования начинается заново. Исходный номер локального журнала может быть больше единицы:
сервер требует строгий порядок внутри эпохи и не допускает возврата к уже применённым номерам.
После частичного воспроизведения локальный экран продолжает считать операции
поверх замороженной доаварийной копии, а не поверх ещё неполного ответа сервера.
Внешняя отправка воспроизводится отдельным результатом после подписанного PDF.
Если физический исход неизвестен, сверка останавливается до решения референта;
размораживание Workspace и включение рабочего офлайна до финальных испытаний
по-прежнему запрещены.

Подготовлен протокол завершения сверки: локальный журнал требует квитанцию для
каждой операции и передаёт серверу число, последнюю последовательность и SHA-256
упорядоченного списка ID. Сервер сравнивает их со своими квитанциями и выдаёт
новую эпоху только при полном совпадении. Повтор после потери HTTP-ответа
возвращает ту же эпоху; если она уже истекла, бот принимает доказанный переход
в новую эпоху только в режиме повторной сверки, без права записи. Локальные
копии писем и пакетов из прежней эпохи удаляются при таком переходе,
чтобы бот не показывал устаревший статус без уже применённого поверх него журнала.
После возвращения связи фоновый цикл снова наполняет копии под новой эпохой.
Серверные задания подготовки, которые ещё не запускались, смогут продолжиться после
снятия барьера. Локальная внешняя отправка с подтверждённым результатом допускает
завершение сверки; неизвестный исход или неподтверждённый результат блокирует его.
Взятое сервером до аварии задание не размораживается, пока его аренда действует.
После истечения аренды сервер переводит физическую отправку в состояние
`delivery_unknown`, требующее ручной проверки; это не повторяет клик.
Это не включает автономный режим в рабочем боте.

Локальный движок покрывает черновики, вложения и основные решения: создание и изменение с
проверенным автором, выбранным согласующим, версией письма и устойчивым
идентификатором операции. Он восстанавливает незавершённые черновики после
перезапуска и не накладывает уже подтверждённые операции повторно на новую
серверную копию. Байтам вложения соответствует SHA-256 в журнале; повтор с тем
же ID и теми же данными не добавляет второе вложение. К живому боту этот движок
подключён к обработчикам Telegram только в автономной фазе.
Автор может удалить без связи только черновик без исходящего номера. Бот немедленно
скрывает его из локальных списков, а сервер при восстановлении принимает удаление
в том же упорядоченном журнале и не воскрешает запись при повторе запроса.
Письмо с выделенным номером автономно не удаляется: закрытие подготовленного
окна и удаление локальной записи робота требуют отдельной сверки; бот сообщает
о необходимости дождаться Workspace. Используется существующая проверка факсимиле:
ошибка Word/COM не считается успешной проверкой, а замена основного DOCX
сбрасывает предыдущий результат. Проверка запускается отдельным циклом на ПК референта.
Локальный движок проверяет отправку на
согласование, возврат с текстом или Opus-аудио и финальное решение с заранее
выданным номером. Аудио привязано к автору решения и версии письма;
незарезервованный номер не создаётся. Доставка аудио автору, подготовка PDF и
серверное воспроизведение этих операций проверены отдельно. Подписание без
отправки также сохраняет каждую PDF-страницу локально, доставляет её автору и
воспроизводит на сервере с проверкой контрольных сумм. Один и тот же DOCX в
разных письмах теперь получает отдельные ключи хранения вложений при сверке.
Бобур может подтвердить подготовленный PDF автономно: робот готовит окно
отправки, а при выключенной автоотправке передаёт решение референту. При
включённой автоотправке создаётся отдельное задание отправки. Исполнитель
сохраняет квитанцию начала до клика E-XAT/Webmail; после подтверждённой доставки
бот и сервер фиксируют результат. При неопределённом исходе администратор сверяет
внешний журнал и подтверждает доставку либо недоставку с пояснением.
Если локальный журнал Exat уже помечает письмо отправленным после прежнего
серверного задания, автономная попытка не присваивает себе этот результат и
не нажимает «Отправить»: оператор сверяет оба журнала вручную.
Полный сценарий аварии, включая работу реальных GUI-адаптеров и переход на ПК
референта, по-прежнему блокирует выпуск автономного EXE.

Проверка на чистой PostgreSQL выявила два препятствия для развёртывания:
длинные ID миграций не помещались в стандартную 32-символьную колонку Alembic,
а аудит действий агента пытался записывать пустого человеческого автора в
обязательное поле. Добавлена подготовительная миграция перед `0060` и новая
миграция после `0063`; все миграции теперь применяются на отдельной тестовой
базе. При откате миграции аудита сначала требуется выгрузить машинные события.

Добавлен серверный протокол аренды записи: назначенный агент может получить
45-секундную эпоху и продлевать её. После истечения аренды Workspace отклоняет
создание, изменения, решения, удаление, загрузку документов/аудио и изменение
согласующих; чтение писем и другие модули остаются доступными. Защита работает
на уровне API и повторно проверяет срок перед фиксацией транзакции. Клиентский
AI Referent показывает режим просмотра и не предлагает изменяющие действия.
Барьер теперь распространяется и на обычные изменяющие маршруты Telegram-бота:
создание и решение писем, файлы, проверки документов, фоновые задания и
синхронизацию реестров. Даже чтение файла фонового задания, которое продлевает
его аренду, требует действующей аренды робота. Новые диапазоны номеров выдаются
только назначенному роботу в действующей эпохе и при включённом флаге.
Повторное чтение уже выданного диапазона с тем же ID возможно при сверке.
Однако `YUKSALISH_AI_REFERENT_OFFLINE_AUTHORITY_ENABLED` по умолчанию выключен:
управляющий контур уже может начать и продлевать аренду, но изменяющие
часть Telegram-действий работает локально только в фазе автономной записи;
внешняя отправка и её сверка реализованы, но ещё не прошли весь аварийный прогон.
**Не включать этот флаг вручную и не ставить такой EXE в производство.**

## Инварианты для полного решения

1. Только один процесс получает обновления Telegram и выполняет E-XAT/Webmail.
   Telegram update сохраняется локально до ответа пользователю и сдвига offset.
2. Каждое действие получает стабильный `operationId`, исходное время и автора.
   Локальный журнал и файлы переживают перезапуск/отключение питания; файл
   сверяется по SHA-256 до воспроизведения. Старое локальное состояние не удаляется
   сразу после первого HTTP 200: требуется подтверждённая серверная сверка.
3. Сервер выдаёт боту ограниченную по времени эпоху владения. Пока эпоха действительна,
   бот не начинает автономные изменения. После её истечения сервер отказывает
   изменяющим действиям AI Referent, даже если Workspace доступен другим клиентам.
   Возобновление записи в Workspace — только после синхронизации и сверки.
   Простое скрытие кнопок в UI не является защитой от прямого API.
4. Сервер атомарно резервирует диапазон исходящих номеров на конкретного агента и
   год. Номер выдаётся локально только из такого диапазона; при исчерпании или смене
   года финальная отправка останавливается. Неиспользованные номера могут дать
   пропуски, но не коллизии.
5. Перед физическим нажатием «Отправить» сохраняется локальная квитанция начала.
   После падения результат считается неизвестным; автоматического повторного клика
   нет. Референт сверяет внешний журнал и фиксирует доказательство результата.
6. Последняя подтверждённая копия Telegram-доступов действует во время аварии.
   Новые ID и новые права до восстановления связи не появляются. При возврате
   сервера журнал сохраняет, какие права были известны на момент решения; отзыв
   доступа влияет на будущие действия, не стирая исторический аудит.
7. Репликация сначала передаёт файлы/аудио, затем операции строго в причинном
   порядке, затем квитанции отправки. Сервер принимает повтор с тем же ID без
   второго эффекта, но отклоняет повтор с другим содержимым. Неустранимый конфликт
   останавливает соответствующий поток и требует ручной сверки, а не тихого слияния.

## Следующие вертикальные этапы

 1. Довести частично подключённые аренду, резерв, локальный маршрут решений и
    сохранение справочников до полной доступности истории, адресатов и документов
    доаварийных писем при отключении сервера.
 2. Проверить E-XAT/Webmail и ручную сверку при падении до и после физического
    клика на реальном ПК, включая повторную автономную эпоху после сверки.
3. Испытать полный повтор после потери ответа на каждом шаге передачи файлов,
   событий и результата отправки.
4. Испытания на тестовых базах: отключение сервера на каждом этапе, авария процесса
   до/после внешнего клика, разделение сети при доступном Workspace, отзыв прав,
   исчерпание резерва, смена года, большие файлы, повторная доставка событий.

До завершения этих этапов действующий сервер остаётся источником решений, а
рабочий EXE не следует заменять экспериментальной сборкой из этой ветки.
