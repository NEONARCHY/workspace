# Zoom-конференции

Модуль `zoom_meetings` бронирует конференции на одном корпоративном Zoom-хосте прямо внутри Workspace. Доменные правила перенесены из отдельного проекта ZoomBot (`C:\projects\zoombot`), чтобы оба продукта вели себя одинаково.

## Решения владельца (2026-09-17)

- ZoomBot **остаётся в эксплуатации** параллельно с модулем. Оба бронируют один и тот же Zoom-аккаунт, но держат разные базы, поэтому занятость сверяется через Zoom API, а не только по таблице Workspace.
- Хост один: две конференции одновременно невозможны.
- Создавать конференции может любой сотрудник с правом `zoom_meetings.create`; чужую изменяет и отменяет только `zoom_meetings.admin`.
- Облачная запись Zoom в модуль не входит: scope `recording:read:admin` не запрашивается и в схеме нет полей записи.

## Как гарантируется непересечение

Два уровня, оба обязательны:

1. **Внутри Workspace** — ограничение PostgreSQL `ex_zoom_meetings_no_overlap` (`EXCLUDE USING gist (tstzrange(starts_at, ends_at) WITH &&) WHERE status IN ('provisioning','scheduled','cancellation_pending')`). Непересечение гарантирует база, а не приложение, поэтому одновременные запросы не могут занять один слот. Расширение `btree_gist` не требуется, пока хост один; при появлении второго хоста в ограничение добавится `host_id`, и расширение станет нужным.
2. **Против бота** — `GET /users/{host}/meetings?type=upcoming`. Перед каждой записью календарь хоста читается заново, при показе дня берётся из кеша `YUKSALISH_ZOOM_AVAILABILITY_CACHE_SECONDS`. Встречи, созданные вне Workspace, показываются в полосе занятости отдельным цветом и без действий.

Окно гонки между проверкой Zoom и записью в Zoom остаётся: Zoom сам не запрещает пересечение. Полностью оно закрывается только выводом бота из эксплуатации.

## Порядок бронирования

```
слот удерживается локально (status=provisioning)
      ↓ ограничение БД отвечает «занято у нас»
календарь Zoom читается заново
      ↓ отвечает «занято вне Workspace»
конференция создаётся в Zoom
      ↓
статус scheduled, сохраняются join_url, passcode, zoom_meeting_id
```

Любой отказ на шагах 2–3 переводит бронь в `failed`, и слот сразу освобождается: `failed` не входит в активные статусы ограничения. Падение процесса между шагами оставляет `provisioning`, который планировщик уведомлений разбирает через 10 минут (`recover_zoom_meetings`); он же повторяет незавершённые отмены в Zoom.

Перенос конференции сначала меняет запись у нас, затем в Zoom; при отказе Zoom локальное изменение откатывается, чтобы две системы не разошлись.

## Правила формы

Перенесены из `app/domain.py` бота без изменений: тема 1–200 символов, описание до 2000, длительность 15–480 минут кратно 15, начало кратно 15 минутам, не в прошлом. Горизонт бронирования ограничен `YUKSALISH_ZOOM_BOOKING_HORIZON_DAYS`. Проверка продублирована в интерфейсе, в Pydantic-схеме и в check-констрейнтах таблицы.

Время хранится в UTC, показывается в `YUKSALISH_ZOOM_TIMEZONE`. Интерфейс собирает момент из календарной даты и времени **организации**, а не машины пользователя: ноутбук с другим часовым поясом не забронирует чужой час.

## Доступ к ссылке

`join_url`, `passcode` и `zoom_meeting_id` отдаются только организатору, приглашённым сотрудникам и администратору модуля. Остальные видят, что слот занят, тему и организатора. Скрытие выполняется на сервере в `zoom_service._meeting_response`, а не в интерфейсе.

## Напоминания

Общий планировщик уведомлений (`notification_scheduler` в `main.py`) раз в минуту создаёт напоминание организатору и приглашённым за `YUKSALISH_ZOOM_REMINDER_MINUTES`. Ключ события содержит идентификатор конференции и время начала: повторный проход молчит, перенос напоминает заново. У встреч, перенесённых из бота, напоминания выключены — пока бот работает, он напоминает в Telegram.

## Настройка сервера

```env
YUKSALISH_ZOOM_ACCOUNT_ID=
YUKSALISH_ZOOM_CLIENT_ID=
YUKSALISH_ZOOM_CLIENT_SECRET=
YUKSALISH_ZOOM_HOST_USER_ID=
YUKSALISH_ZOOM_TIMEZONE=Asia/Tashkent
YUKSALISH_ZOOM_REMINDER_MINUTES=30
YUKSALISH_ZOOM_BOOKING_HORIZON_DAYS=180
```

На LAN-сервере эти переменные должны лежать **и** в `.env.lan`, и в `.env`: контейнер API берёт набор из того файла, с которым его пересоздали, а переменные, заданные только в одном файле, при перезапуске из другого тихо выключают раздел. См. `docs/operations/lan-web-workspace.md`.

Пока любое из первых четырёх значений пусто, модуль отвечает `configured: false`, экран объясняет это словами, а запись возвращает 503. Приложение в Zoom Marketplace — типа **Server-to-Server OAuth** со scopes на чтение пользователя-хоста и создание, чтение, изменение и удаление встреч. Секреты живут только в `.env` сервера и никогда не попадают в renderer и в логи.

## Перенос встреч из бота

`scripts/import_zoombot_meetings.py` разово переносит будущие `scheduled`-встречи из SQLite бота. Бот опознаёт людей по Telegram ID, Workspace — по учётной записи, поэтому нужен файл соответствия:

```powershell
.venv\Scripts\python.exe scripts\import_zoombot_meetings.py --template owners.csv
# заполнить столбец workspace_username
.venv\Scripts\python.exe scripts\import_zoombot_meetings.py --mapping owners.csv --dry-run
.venv\Scripts\python.exe scripts\import_zoombot_meetings.py --mapping owners.csv --apply
```

Без `--apply` скрипт только показывает план. Встречи без сопоставленного сотрудника всё равно переносятся под сохранённым в боте именем и остаются без владельца — иначе их слот молча отдали бы другому. Повторный запуск пропускает уже перенесённые конференции по `zoom_meeting_id`. В Zoom скрипт ничего не создаёт: эти конференции там уже есть.
