# Исполнение входящих писем в Workspace

AI Referent принимает и регистрирует письма. Раздел «Входящие письма» по умолчанию
показывает этот локальный реестр; назначение и исполнение работают без сервера ЭДО.
Прежний раздел сохранён на вкладке «Письма из ЭДО», включая старые числовые ссылки,
права, файлы и передачу результата обратно в ЭДО. Два реестра не объединяются по
номеру письма: совпадение номеров не подтверждает совпадение документов.

## Первый законченный сценарий

1. Сотрудник с доступом к исходному письму и правами `incoming_letters.edit`,
   `tasks.view/create` открывает письмо, проверяет опубликованные документы и
   задаёт поручение, активного исполнителя, до 50 соисполнителей и будущий срок.
2. Только подтверждение создаёт обычную задачу. Одна исходная запись имеет одно
   поручение. Срок передаётся с часовым поясом; назначения не угадываются по имени
   ответственного робота. Документы копируются в отдельные объекты хранилища и
   становятся приватными вложениями задачи. Отсутствие ожидаемых оригиналов
   блокирует назначение. Весь показанный пакет ограничен 100 файлами и 200 МиБ.
3. «Открыть поручение» открывает существующую карточку задачи: соисполнители,
   комментарии, файлы, срок, отчёт, проверка и возврат используют её действующие
   защищённые операции, уведомления, чат и аудит. Письмо показывает текущие данные
   этой же задачи, без второго состояния исполнения. Методика эффективности
   остаётся обычной методикой задач; отдельный показатель документооборота не вводится.

Существующие письма не превращаются в задачи автоматически. Изменение регистрации
роботом сохраняет ссылку на задачу и не перезаписывает её срок, участников, результат
или копии оригиналов. Новые версии документов остаются доступны в исходной карточке;
ранее созданное поручение сохраняет снимок на момент назначения. Несколько резолюций,
индивидуальные сроки соисполнителей и обратная передача исполнения в E-XAT не входят
в этот этап. Уже назначенную задачу нельзя удалить вместе с историей связи;
используется действующая отмена задачи.

## Права и API

GET `/api/v1/incoming-documents` поддерживает поиск, пагинацию и фильтры исполнения.
GET `/{id}` возвращает карточку и опубликованные файлы. GET `/{id}/files/{file_id}`
и `/preview` повторяют проверку доступа, владельца файла и контрольной суммы.
Office-предпросмотр ограничен 25 МиБ и двумя параллельными обработками.

`incoming_letters.view` обязателен для каждого маршрута. Исходный реестр доступен
строго в области AI Referent, включая модульное право и персональную видимость.
Дополнительно постановщик, основной исполнитель и явные участники связанной задачи
видят порученное письмо. Это назначение не открывает остальные письма референта.
Открытие самой задачи проверяет её обычную область и `tasks.view`. Передача документов
в задачу явно распространяет на копии обычную политику доступа к задачам, включая
действующий контроль руководителей; права исходного архива не расширяются.

POST `/{id}/execution` принимает `operationId`, `expectedRevision`, `instruction`,
`assigneeId`, `coAssigneeIds`, `fileIds`, `dueAt`. Исходная запись блокируется до
завершения назначения. Ревизия и набор опубликованных файлов сверяются повторно;
изменение требует перечитать карточку. Один и тот же запрос с тем же operationId
возвращает существующую задачу, включая повтор после новой синхронизации источника.
Другой запрос для уже назначенного письма возвращает 409.

Создание задачи, её вложений, связи и аудита атомарно. При известном отказе до
COMMIT изменения откатываются, созданные копии удаляются. При неизвестном результате
COMMIT файлы сохраняются: повтор с прежним operationId проверяет сохранённый итог.
Клиент не повторяет запись автоматически и сохраняет ввод до сверки состояния.

## Выпуск и проверка

Сначала применить `alembic upgrade head` до `0128_merge_incoming_telegram`, затем
обновить API, после этого web/desktop. Объединяющая ревизия сохраняет обе параллельные
ветки `0127_incoming_document_execution` и `0127_notification_mirror`, не изменяя их.
Миграция исполнения добавляет только таблицу связей; записи референта,
письма ЭДО и существующие задачи не изменяются. До назначения проверить, что робот
передаёт сами файлы в хранилище Workspace, а не только строки журнала. Откат миграции
удаляет связи; после рабочих назначений его нельзя выполнять как обычный откат кода.

`tests/python/test_incoming_document_workflow.py` проверяет реальный PostgreSQL и HTTP:
области и файлы, конкурентное назначение, повторы, обновление источника, откат при сбое
копирования, сроки, фильтры и цикл отчёт → возврат → повторный отчёт → принятие.
`IncomingDocumentsView.test.tsx` проверяет подтверждение, сохранение ввода,
сверку состояния, двойное нажатие, отсутствие оригиналов и переход к старой ЭДО.

Рабочий офисный сервер этой веткой автоматически не обновляется. Проверки выполняются
на отдельной тестовой PostgreSQL и синтетических документах.
