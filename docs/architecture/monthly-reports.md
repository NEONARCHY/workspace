# Ойлик ҳисоботлар

Ежемесячные отчёты Центрального аппарата — отдельный раздел внутри ИИ-модулей.
Он использует существующие авторизацию, назначения руководителей, уведомления,
объектное хранилище и общий диалог Workspace. Ежедневный AI Hisobot не меняется.

## Отчётный месяц и сроки

Время считается в Asia/Tashkent. С 20-го до последнего дня месяца активен текущий
месяц, с 1-го по 5-е включительно — предыдущий. С 6-го по 19-е блок статистики
скрыт; история раздела доступна постоянно. Пропущенные отчёты за уже открытые
месяцы можно досдать, пока первый заместитель не разрешил начисление.

Напоминание начинается за три рабочих дня строго до календарного конца месяца.
Например, для ноября 2026 без исключений это 25 ноября: 27, 26 и 25 ноября.
По умолчанию рабочие дни — понедельник–пятница. Администратор задаёт праздники
и рабочие выходные в рабочем календаре раздела; официальные переносы не угадываются.
Изменение исключения пересчитывает дату незакрытого месяца. При переносе напоминания
вперёд прежнее действие скрывается до нового срока. Начисление уже закрытого месяца
и его снимок не меняются.

Первое обращение или фоновая проверка в период сбора атомарно создаёт месяц и
фиксирует имена, подразделения и активный состав ЦА. Региональные подразделения
и их дочерние подразделения исключены. Сотрудники без подразделения относятся
к ЦА по действующему правилу справочника. Кадровые изменения после фиксации
не переписывают прежний состав и статистику. Исторические месяцы не восстанавливаются
по текущему справочнику. После запуска сервера внутри периода сбора снимок
фиксируется в момент первого обращения; точный состав на прошлое 20-е не выдумывается.

Напоминания создаёт штатный scheduler API, ключ уникален для сотрудника и месяца.
Отправка отчёта, разрешение начисления и закрытие окна сбора разрешают прежние
напоминания. Окно показывается раз в день для сотрудника на устройстве, ждёт
закрытия другого диалога и не отправляет ничего автоматически. Уведомление остаётся
в общем центре; отключённые всплытия ОС сохраняют прежнее поведение.

## Файлы и история

Предоставленный владельцем `oylik hisobot (2).docx` поставляется без изменения
как `hr_assets/monthly-report-template.docx`. SHA-256:
`343a4865431c4e74bbdc07f765214ee6c1f7626a5bc0d2e3b92e0839c27c787a`.
В исходном DOCX написано «понедельник до 10:00»; это текст шаблона, а не инструкция
для планировщика. Правило владельца о трёх рабочих днях имеет приоритет.
Шаблон скачивается через авторизованный endpoint из раздела и окна напоминания.

Каждая отправка содержит от одного до пяти непустых файлов: каждый до 25 МБ,
вместе до 50 МБ. Сохраняются отдельная неизменяемая версия, время, комментарий
и манифест закрытых объектов. Новая версия не удаляет старую. Повтор с прежним
ID и тем же содержимым возвращает прежний результат, включая повтор после
разрешения ЗП; иной запрос с тем же ID получает конфликт. При ошибке интерфейс
сохраняет выбранные файлы, комментарий и ключ для повтора; закрытие отдельного
окна в пределах сеанса также сохраняет его форму. Файлы браузерной формы
не сохраняются после перезапуска приложения.

Ключи хранилища клиенту не возвращаются. Скачивание всегда проверяет владельца
или текущего председателя/первого заместителя; администраторы сохраняют просмотр.
Обычный сотрудник не получает чужие имена и файлы. Бухгалтер получает решение
по месяцу, без доступа к чужим файлам. Выдача файлов — attachment, no-store,
nosniff. Незавершённая загрузка очищает созданные объекты. При неизвестном исходе
COMMIT объекты сохраняются: удалять возможно уже подтверждённые файлы нельзя.

## Разрешение на начисление

Председатель определяется настройками HR, первый заместитель — существующим
однозначным активным назначением должности `Rais birinchi…`, главный бухгалтер —
настройками HR. Название роли на клиенте не даёт полномочий. Только действующий
первый заместитель с правом согласования раздела может разрешить начисление.
Администратор не подменяет это решение. Неоднозначное назначение заместителя
или отсутствие активного бухгалтера не заменяется случайным сотрудником.

Перед решением интерфейс показывает сдавших и несдавших. Первый заместитель
может явно подтвердить разрешение при наличии несдавших. Комментарий необязателен.
Решение закрывает изменения отчётов и фиксирует автора, время, получателя,
комментарий, численность и ID последних версий. Блокировка месяца сериализует
отправку/замену отчёта и решение. Повтор не создаёт второе уведомление.

Главный бухгалтер получает сохраняемое уведомление и окно разрешения; получение
можно подтвердить. Закрытие окна без подтверждения не удаляет уведомление.
Это разрешение в Workspace, а не автоматическая проводка или начисление в 1С.

## Поставка и проверки

Миграция `0122_monthly_reports` после `0121_ai_referent_rejection` создаёт четыре
новые таблицы и расширяет допустимый раздел уведомлений. Существующие отчёты,
зарплаты и файлы не изменяются. Откат намеренно не удаляет накопленные документы
и решения. Перед выпуском нужен резервный снимок БД; затем миграция и API,
после них web/desktop. Проверить назначения HR, единственного первого заместителя
и рабочие исключения ближайшего месяца. Простое обновление клиента не применяет миграцию.
Серверный образ включает только явно разрешённый шаблон DOCX; остальные документы
по-прежнему исключены из контекста сборки. После появления новых уведомлений откат
API требует совместимой версии, понимающей новую секцию уведомлений.

Проверки: `test_monthly_reports.py`, `test_monthly_reports_api.py`,
`MonthlyReportsView.test.tsx` и общие тесты оболочки, модулей и уведомлений.
Изолированная browser QA: Vite на `127.0.0.1:5193`, затем
`node scripts/qa/monthly-reports-smoke.cjs`; все API перехвачены, данные синтетические.
Проверка renderer не заменяет проверку установленного EXE и рабочего сервера.
